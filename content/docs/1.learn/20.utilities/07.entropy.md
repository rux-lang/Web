# Entropy

::note
<!-- sync:needs:start -->

**You'll need**: [Distribution](/docs/learn/distribution), [Catch](/docs/learn/catch), [Enum](/docs/learn/enum), [Pointer](/docs/learn/pointer)
<!-- sync:needs:end -->

::

A seeded generator is predictable by design: anyone who learns the seed can replay every number it will ever produce. For a simulation that is a feature. For a session token, a password salt or an encryption key it is a disaster: those numbers must be ones nobody can guess, so they cannot come from arithmetic inside the program.

They come from outside it. The operating system collects unpredictability (**entropy**) from hardware and from the timing of events, and the `Entropy` package asks it for some:

```rux
import Entropy::{ EntropyError, Fill, NextUint64 };
import Random::{ Pcg64Dxsm, PcgFromEntropy, UniformBelow };
```

The output is different on every run, and that is exactly what this lesson is about.

## Every request can fail

Asking the system can fail: it may have no source, the request may be interrupted, or the system may simply refuse. So every function here can fail with an `EntropyError`, an [enum](/docs/learn/enum) saying why — `NextUint64` returns `uint64 ! EntropyError`, `Fill` returns `!EntropyError` — and every call has to deal with that outcome:

| Function           | Returns     | Gives you                                    |
| ------------------ | ----------- | -------------------------------------------- |
| `NextUint64()`     | `uint64`    | one unpredictable 64-bit number              |
| `Fill(buffer, n)`  | —           | `n` unpredictable bytes, written to `buffer` |
| `PcgFromEntropy()` | `Pcg64Dxsm` | a generator with an unguessable seed         |

The whole point of these numbers is that nobody can guess them. An error quietly replaced by some fixed value (a `catch` that answers `0`) would produce a "random" key that is the same on every machine. So the program handles every call and stops if one fails.

`Describe` turns the reason into words, and `IsTransient` says whether asking again might help:

```rux
func Describe(error: EntropyError) {
    let why = match error {
        EntropyError::Unsupported => "this system has no entropy source",
        EntropyError::Interrupted => "the request was interrupted",
        EntropyError::Failed => "the system refused",
        EntropyError::TooLarge => "too many bytes in one request"
    };
    // `IsTransient` says whether asking again might help. Only an interruption is worth a retry.
    PrintLine("no entropy: {} (worth retrying: {})", why, error.IsTransient());
}
```

## One number

`NextUint64` is the simplest request. A [`catch`](/docs/learn/catch) takes the value, or describes the error and ends the program with status 1. The arm's `return 1` leaves `Main`, so after the `catch`, `value` is always a real number:

```rux
let value = NextUint64() catch {
    error => {
        Describe(error);
        return 1;
    }
};
PrintLine("a 64-bit value  {:#018x}", value);
```

`{:#018x}` prints it in hexadecimal with a `0x` prefix, padded with zeros to 18 characters (the prefix and all 16 digits).

## A buffer of bytes

A key is usually a run of bytes rather than one number. `Fill` writes as many bytes as you ask for into memory you provide, so it takes a [pointer](/docs/learn/pointer) to the first byte and a count:

```rux
var key: byte[16] = [0; 16];
// Safety: `key` is a local array of 16 bytes, so the address of its first byte is writable
// for all 16.
Fill(@key[0] as *var opaque, 16) catch {
    error => {
        Describe(error);
        return 1;
    }
};
```

`@key[0]` is the address of the first byte. `Fill` takes the buffer as `*var opaque` (a writable pointer to bytes of any type), because it neither knows nor cares what the bytes will be used for. It also cannot see how big the buffer is: the count you pass is all it has, so it must match the array. Nothing can check that promise — writing through a raw pointer is one of the [raw operations](/docs/lang/pointers/overview#raw-operations) the compiler takes on trust — so the caller makes it, in a `// Safety:` comment above the call that says why the count is right.

The [`catch`](/docs/learn/catch) here names the error, `error => { … }`, so the arm can pass it to `Describe`.

## The common use: an unguessable seed

Every request for entropy is a call into the operating system, while a generator makes a number in a few instructions, and a program rarely needs all its numbers to be unguessable. The usual pattern takes a little entropy once, as a seed, and then draws from a fast generator as in [Distribution](/docs/learn/distribution):

```rux
var generator = PcgFromEntropy() catch {
    error => {
        Describe(error);
        return 1;
    }
};
PrintLine("a die roll      {}", UniformBelow<Pcg64Dxsm>(&var generator, 6) + 1);
```

## The program

The whole lesson is one package in the [Examples repository](https://github.com/rux-lang/Examples/tree/main/Utilities/Entropy). Its comments explain every step.

<!-- sync:program:start -->

```rux [Src/Main.rux]
// A seeded generator is predictable by design: anyone who learns the seed can replay it. When
// the numbers must be unguessable, such as a session token, a password salt, or the seed for a
// simulation that should differ every run, they have to come from outside the program.
//
// The operating system collects unpredictability from hardware and timing, and the Entropy
// package asks it for some. `NextUint64()` returns a `uint64` and `Fill` fills a buffer, and
// both can fail with an `EntropyError`. Asking can fail (a system may have no source, or the
// request may be interrupted), and since the whole point is that the bytes are unguessable, an
// error must never be quietly replaced by some fixed value. So every call here is handled.
//
// The output is different on every run, which is exactly what this lesson is about.
import Entropy::{ EntropyError, Fill, NextUint64 };
import Io::{ Print, PrintLine };
import Random::{ Pcg64Dxsm, PcgFromEntropy, UniformBelow };

func Describe(error: EntropyError) {
    let why = match error {
        EntropyError::Unsupported => "this system has no entropy source",
        EntropyError::Interrupted => "the request was interrupted",
        EntropyError::Failed => "the system refused",
        EntropyError::TooLarge => "too many bytes in one request"
    };
    // `IsTransient` says whether asking again might help. Only an interruption is worth a retry.
    PrintLine("no entropy: {} (worth retrying: {})", why, error.IsTransient());
}

func Main() -> int {
    // One unpredictable 64-bit number.
    let value = NextUint64() catch {
        error => {
            Describe(error);
            return 1;
        }
    };
    PrintLine("a 64-bit value  {:#018x}", value);

    // Sixteen unpredictable bytes, written into a buffer through a raw pointer. `Fill` cannot
    // check that the pointer addresses as many bytes as it is told to write, so the caller
    // promises it, in a `// Safety:` comment that says why it holds.
    var key: byte[16] = [0; 16];
    // Safety: `key` is a local array of 16 bytes, so the address of its first byte is writable
    // for all 16.
    Fill(@key[0] as *var opaque, 16) catch {
        error => {
            Describe(error);
            return 1;
        }
    };
    Print("a 16-byte key  ");
    for b in key {
        Print(" {:02x}", b);
    }
    PrintLine();

    // The common use: seed a fast generator once from entropy, then draw from it as usual.
    // `PcgFromEntropy` returns a `Pcg64Dxsm` or fails with an `EntropyError`, so the seeding is
    // handled too.
    var generator = PcgFromEntropy() catch {
        error => {
            Describe(error);
            return 1;
        }
    };
    PrintLine("a die roll      {}", UniformBelow<Pcg64Dxsm>(&var generator, 6) + 1);
    return 0;
}
```

Besides `Io`, its `Rux.toml` lists `Entropy` and `Random` under `[Dependencies]`.

## Common mistakes

::mistake
**Using the outcome as a number.**\
`NextUint64` can fail, so its result is a `uint64 ! EntropyError`, not a `uint64`. Writing `let raw: uint64 = NextUint64();` fails with:

```text
error: cannot assign 'uint64 ! EntropyError' to 'uint64'
```

Decide what an error means here, with `catch`, as the program does.
::

::mistake
**Passing the array instead of its address.**\
`Fill(key, 16)` fails with:

```text
error: argument 1 to 'Fill' has type 'uint8[16]', but parameter 'buffer' requires '*var opaque'
```

Pass the address of the first byte: `@key[0]`.
::

::mistake
**Leaving `Fill`'s outcome unused.**\
`Fill` returns nothing on success, but it can still fail. A bare `Fill(@key[0] as *var opaque, 16);` fails with:

```text
error: 'Fill' can fail with 'EntropyError', and the result is not used
help: pass the error on with '!', ignore it with '!!;', or handle it with 'catch { ... }'
```

Of the three, ignoring it is the wrong one here: after a failed `Fill`, `key` would still be sixteen zeros.
::

::mistake
**Covering an error with a fixed value.**\
A fallback such as `NextUint64() !! 0` compiles, and turns a missing entropy source into a key everyone knows. When unpredictability is the point, stop, retry if `IsTransient()` says it may help, or report the error. Never invent the bytes.
::

::mistake
**A seeded generator where secrets are needed.**\
`Pcg64Dxsm` is fast and good for simulations, but it is not designed to resist someone who is trying to predict it, even with an unguessable seed. Draw passwords, tokens and keys straight from `Fill` or `NextUint64`, as the [Password](/docs/learn/password) project does.
::

## Try it yourself

1. Run the program three times. Which lines change?
2. Make the key 32 bytes long. What else has to change besides the array's size?
3. Replace the `PcgFromEntropy()` call and its `catch` with `Pcg64Dxsm::New(2026)` (the constructor cannot fail, so there is nothing to catch) and run twice. What happens to the die roll?
4. Leave out one arm of the `match` in `Describe` and read the compiler's message.
