# Arc

::note
<!-- sync:needs:start -->

**You'll need**: [Rc](/docs/learn/rc), [Thread](/docs/learn/thread), [Atomic](/docs/learn/atomic)
<!-- sync:needs:end -->

::

A thread can outlive the line that started it, so whatever it is given must last as long as the thread does. So far there were two ways to arrange that, and both have a catch:

- **Giving** a value away to the thread, as [Thread](/docs/learn/thread) did, gives it to one thread. Several threads that need the same large value would each need their own copy.
- **A pointer** to a local, as [Atomic](/docs/learn/atomic) did, shares one value — but only for as long as the local lives, which the compiler cannot check, so every use rests on a `// Safety:` promise.

An `Arc<T>` — an _atomically reference-counted_ handle — removes the catch. It is the [`Rc<T>`](/docs/learn/rc) you already know, made safe to use across threads:

```rux
import Allocator::SystemAllocator;
import Allocator::Pointers::Arc;
```

## Making one

An `Arc` takes a value onto the heap, next to a count of the handles that share it, and returns the first handle. The storage comes from an [allocator](/docs/learn/allocator), so making one can fail. The constructor, `Arc<Shop>::New(allocator, value)`, stops the program when there is no storage; `Arc::TryCreate` is declared `-> Arc<T> ! AllocError` instead, so the program can [`catch`](/docs/learn/catch-fallback) the refusal and leave:

```rux
let stock = Shop { prices: [120, 250, 75, 499], sold: Atomic<uint64>::New(0) };
var shop = Arc::TryCreate<Shop>(SystemAllocator::New(), stock) catch { _ => return 1 };
```

`stock` is given away to the `Arc`, which owns it from then on.

The allocator must be one every thread can use. `SystemAllocator` is.

## Clones are handles

A handle owns its share of the value, so it is never copied behind your back. `Clone` makes another handle: it points at the same value and adds one to the count. The value itself is never duplicated, however large it is. Each till gets a clone, which goes to its thread with the rest of the till:

```rux
let first = Spawn(Ring, Till { orders: [1, 0, 2, 0], shop: shop.Clone() }) catch { _ => return 1 };
let second = Spawn(Ring, Till { orders: [0, 3, 0, 1], shop: shop.Clone() }) catch { _ => return 1 };
let third = Spawn(Ring, Till { orders: [2, 2, 2, 2], shop: shop.Clone() }) catch { _ => return 1 };
var tills: JoinHandle<uint64>[3] = [first, second, third];
```

```mermaid
flowchart LR
    m["`Main`'s handle"] --> b["count: 4<br/>the `Shop`"]
    t1["till 1's handle"] --> b
    t2["till 2's handle"] --> b
    t3["till 3's handle"] --> b
```

Dropping a handle subtracts one, and whichever handle is last — on whichever thread — destroys the value and returns its storage. That is the one difference from `Rc<T>`: an `Rc` keeps its count with plain arithmetic, and two threads changing it at once would lose a count, just as in the race in [Atomic](/docs/learn/atomic). An `Arc` changes its count with atomic operations, so clones can be made and dropped on any thread at the same moment. The compiler holds you to it: `Spawn` takes only a context and a result that are [`Sendable`](/docs/api/core/sendable), an `Rc` is marked `#Unsendable` to stay on the thread that made it, and so `Spawn` refuses one.

| Method                        | Returns                                                            |
| ----------------------------- | ------------------------------------------------------------------ |
| `Arc<T>::New(a, value)`       | the first handle; stops the program when there is no storage       |
| `Arc::TryCreate<T>(a, value)` | the first handle; fails with `AllocError` when there is no storage |
| `Clone()`                     | another handle to the same value                                   |
| `Get()`                       | `&T`, the value, for reading                                       |
| `GetMutable()`                | `&var T?`, the value for writing, only while one handle exists     |
| `Count()`                     | how many handles share the value right now                         |
| `SameAs(other)`               | whether two handles share one value                                |

After the joins, every till has finished and dropped its clone, so `Count` is back to 1.

## Reading, and changing

Through an `Arc<T>`, the value is only read: `Get` returns a read-only [reference](/docs/learn/reference), `&T`. Several threads read it at once, and reading never races with reading.

Whatever must change while the value is shared needs synchronization of its own, inside the `Arc`. Here that is the `sold` counter, an `Atomic<uint64>` in the shared `Shop`:

```rux
struct Shop {
    prices: uint64[4];
    sold: Atomic<uint64>;
}
```

```rux
func Ring(till: Till) -> uint64 {
    let shop = till.shop.Get();
    var revenue: uint64 = 0;
    for index in 0..4 {
        revenue = revenue + till.orders[index] * shop.prices[index];
        shop.sold.FetchAdd(till.orders[index]);
    }
    return revenue;
}
```

The only other way to write is `GetMutable`, which gives a `&var T` only while a single handle exists — when nobody else could be reading — and none otherwise. At the end, `Main` holds the last handle and changes a price in its `value?` arm:

```rux
match shop.GetMutable() {
    value? => value.prices[0] = 110,
    none => PrintLine("still shared"),
}
```

Just before that, `Inspect(shop.Clone(), &shop)` passes a clone by value next to a [written loan](/docs/lang/functions/parameters#written-loans) of `Main`'s own handle. The clone lives as long as the call runs, so `Inspect` sees two handles; once it returns, `Main`'s is the only one again.

`Mutex<T>` and the other types of the `Sync` package are handles already, with a `Clone` of their own, so they need no `Arc` around them. `Arc` is for everything else: a table, a configuration, a struct of atomics.

## The program

The whole lesson is one package in the [Examples repository](https://github.com/rux-lang/Examples/tree/main/Concurrency/Arc). Its comments explain every step.

<!-- sync:program:start -->

```rux [Src/Main.rux]
// A thread outlives the line that started it, so whatever it is given must last as long as the
// thread does. Giving a value away to it works for one thread. Several threads that need the same
// large value would each need a copy, and a pointer to a local is only safe while that local lives.
//
// An `Arc<T>` (atomically reference-counted) puts one value on the heap and shares it between
// handles. A handle owns its share, so it is never copied implicitly: `Clone` makes another
// handle, which only adds one to a count; the value itself is never duplicated.
// Dropping a handle subtracts one, and the last handle to go destroys the value. It is the `Rc<T>`
// of the Rc lesson with one difference: the count changes through atomic operations, so clones
// can be made and dropped on different threads at the same time.
//
// Through an `Arc<T>` the value is only read. Whatever in it must change while it is shared needs
// its own synchronization, such as an `Atomic<T>` or a `Mutex<T>` inside it.
import Allocator::SystemAllocator;
import Allocator::Pointers::Arc;
import Atomic::Atomic;
import Io::PrintLine;
import Thread::{ JoinHandle, Spawn };

// What every till shares: a price list nobody changes, and a counter they all add to.
struct Shop {
    prices: uint64[4];
    sold: Atomic<uint64>;
}

// What a till is given: its own orders, and a handle to the shop.
struct Till {
    orders: uint64[4];
    shop: Arc<Shop>;
}

// Prices the orders from the shared list and counts the items in the shared total. `Get` gives a
// read-only `&Shop`, so `shop.prices[0] = 110;` here is refused:
//
//     error: cannot modify data through immutable reference '&Shop'
func Ring(till: Till) -> uint64 {
    let shop = till.shop.Get();
    var revenue: uint64 = 0;
    for index in 0..4 {
        revenue = revenue + till.orders[index] * shop.prices[index];
        shop.sold.FetchAdd(till.orders[index]);
    }
    return revenue;
}

// A clone shares the value rather than duplicating it.
func Inspect(copy: Arc<Shop>, original: &Arc<Shop>) {
    PrintLine("same shop       {}", copy.SameAs(original));
    PrintLine("handles now     {}", original.Count());
}

func Main() -> int {
    // The first handle. Its storage comes from an allocator, so making it can fail: `TryCreate`
    // fails with the refusal, where `Arc::New` would stop the program.
    let stock = Shop { prices: [120, 250, 75, 499], sold: Atomic<uint64>::New(0) };
    var shop = Arc::TryCreate<Shop>(SystemAllocator::New(), stock) catch { _ => return 1 };
    PrintLine("handles before  {}", shop.Count());

    // Each till gets a clone of the handle. Every clone points at the same shop, and goes to its
    // thread with the rest of the till. Writing `shop: shop` instead gives `Main`'s own handle
    // away, because a handle is never copied behind your back, and the next use is refused:
    //
    //     error: 'shop' is used after it was given away
    let first = Spawn(Ring, Till { orders: [1, 0, 2, 0], shop: shop.Clone() }) catch { _ => return 1 };
    let second = Spawn(Ring, Till { orders: [0, 3, 0, 1], shop: shop.Clone() }) catch { _ => return 1 };
    let third = Spawn(Ring, Till { orders: [2, 2, 2, 2], shop: shop.Clone() }) catch { _ => return 1 };
    var tills: JoinHandle<uint64>[3] = [first, second, third];
    for index in 0..3 {
        PrintLine("till {} took     {}", index + 1, tills[index].Join());
    }

    // Every till has finished and dropped its clone, so only `Main`'s handle is left.
    PrintLine("items sold      {}", shop.Get().sold.Load());
    PrintLine("handles after   {}", shop.Count());

    // A clone passed by value lives for as long as the call runs, so meanwhile there are two.
    Inspect(shop.Clone(), &shop);

    // The clone went with the call, so this is the only handle again, and it may change the value.
    match shop.GetMutable() {
        value? => value.prices[0] = 110,
        none => PrintLine("still shared"),
    }
    PrintLine("first price     {}", shop.Get().prices[0]);
    return 0;
}
```

## Common mistakes

::mistake
**Writing through `Get`.**\
`Get` returns a read-only reference, so `shop.prices[0] = 110;` in `Ring` fails with:

```text
error: cannot modify data through immutable reference '&Shop'
```

Put what changes in an atomic or a mutex inside the shared value, or use `GetMutable` once the handle is the only one.
::

::mistake
**Giving away the handle instead of a clone.**\
`Till { orders: [1, 0, 2, 0], shop: shop }` compiles on its own: it gives `Main`'s handle to the first till. Every later use of `shop` then fails with:

```text
error: 'shop' is used after it was given away
  help: lend it with '&shop' where it is only read, or clone it where both uses need a value
```

A handle is never copied behind your back. Give each till `shop.Clone()`.
::

::mistake
**Sending an `Rc` to another thread.**\
An `Rc` changes its count with plain arithmetic, and two threads changing it at once could free the value while a handle still points at it. `Spawn(Read, shared.Clone())` with an `Rc<uint64>` fails with:

```text
error: type argument 'Rc<uint64>' does not satisfy interface bound 'Sendable' on type parameter 'T'
  note: 'Rc<uint64>' is declared '#Unsendable', so it stays on the thread that made it
  note: type parameter 'T' of function 'Spawn' is bound by 'Sendable'
  help: keep the value on the thread that made it, or share it through a type made for threads, such as 'Arc' in place of 'Rc'
```

Across threads, use `Arc`.
::

::mistake
**Trusting `Count` while threads run.**\
Other threads clone and drop handles at any moment, so the count can be stale as soon as it is read. It is exact only when no other thread holds a handle — as after the joins here.
::

::mistake
**A cycle of handles.**\
There are no weak handles. Two values that hold `Arc`s to each other keep each other's count above zero, and neither is ever freed.
::

## Try it yourself

1. Add a fourth till, and check that `handles after` is still 1.
2. Count the revenue in the shop too: add a `revenue: Atomic<uint64>` field to `Shop`, add to it in `Ring`, and compare it with the sum of what the tills returned.
3. Print `shop.GetMutable() != none` just before the joins instead of after them. Can you predict what it prints? Why not?
