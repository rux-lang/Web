# Part 9: Errors

An [optional](/docs/learn/optional) can say that a value is missing, but never why. This part gives a failure a voice. A function declared `-> T ! E` returns a `T` or fails with an error of type `E` saying what went wrong. A call to it gives back a _fallible_ (one value holding either the success or the error), and the compiler makes sure no error is ever dropped without the code saying so: a fallible that nothing uses does not compile. By the end of the part you can write functions that fail precisely, decide at each call whether to handle an error or pass it on, and tell a failure the caller can fix from a bug that should stop the program.

## What you will learn

- Declaring an error with `-> T ! E`, or `-> !E` when there is no answer, and leaving with `throw`.
- What a call gives back: a fallible `T ! E`, taken apart with `match` by side, tested with `is`, and kept as a value when the outcome must outlive the call.
- Why an unused fallible does not compile, and dropping an error on purpose with `F() !!;` or turning it into `none` with `F() !! none`.
- Handling an error with `F() catch { arms }` (one arm per case) or replacing every error with `F() !! fallback`.
- Passing an error to the caller with a postfix `!`, and adding context on the way with `catch { e => throw Mapped(e) }`.
- Designing error types: a variant of cases, or a sum of unrelated errors `A | B`.
- Keeping `Main` as `func Main() -> int`, which cannot fail, turning absence into an error with `?? throw`, and nesting `-> T? ! E`.
- `Panic`, `Assert` and `DebugAssert` for the situations only a bug can reach.

## Which error tool?

Most of this part is choosing the right tool for one moment in the code. The questions run in this order:

```mermaid
flowchart TD
    start(["Something can go wrong"]) --> bug{"Can it happen in a<br/>program with no bugs?"}
    bug -- "no, only a bug" --> stop["`Panic`, `Assert`,<br/>`DebugAssert`<br/>9.15–9.16"]
    bug -- "yes" --> why{"Does the caller<br/>need to know why?"}
    why -- "no" --> opt["An optional `T?`<br/>Part 8"]
    why -- "yes" --> fal["`-> T ! E`, or `-> !E`<br/>9.1–9.3"]
```

Once a function is fallible, each call decides what its error means:

| Who decides what the error means?              | Write                                                   | Lesson    |
| ---------------------------------------------- | ------------------------------------------------------- | --------- |
| This function, and the reason matters          | `F() catch { arms }`, one arm per case                  | 9.6       |
| This function, and the reason does not matter  | `F() !! fallback`, `!! none`, or a deliberate `F() !!;` | 9.5, 9.7  |
| Later, as data                                 | the fallible itself, `let kept = F();`                  | 9.4       |
| The caller, and the error already fits its own | `F()!` passes it on                                     | 9.8, 9.11 |
| The caller, with a different error or context  | `catch { e => throw Mapped(e) }`                        | 9.10      |

## Before you start

Finish [Part 8: Optionals](/docs/learn/optionals) first: errors are built on the same ideas, and several lessons compare the two side by side. You also need [variants](/docs/learn/variant) from Part 6 and the patterns of [Part 7](/docs/learn/patterns). Each lesson's package is in the Examples repository's `Errors/` folder:

```sh
cd Examples/Errors/Fallible
rux run
```

## After this part

[Part 10: Sum types](/docs/learn/sum-types) takes the `A | B` you met in [Error sum](/docs/learn/error-sum) and makes it a type of its own, usable anywhere. Before moving on, try the checkpoint project [Calculator](/docs/learn/calculator): it evaluates sums and key-press tapes where every way a calculation can fail is a case of an error variant.

For the rules behind this part, see [Errors](/docs/lang/errors/overview), [Fallible values](/docs/lang/errors/fallible-values), [Handling errors](/docs/lang/errors/handling), [Passing errors on](/docs/lang/errors/propagation) and [Panics](/docs/lang/errors/panics) in the Rux Reference, and [Panic](/docs/api/core/diagnostics#panic) and [Assert](/docs/api/core/diagnostics#assert) in the API reference.
