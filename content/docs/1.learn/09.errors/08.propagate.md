# Propagate

::note
<!-- sync:needs:start -->

**You'll need**: [Outcome](/docs/learn/outcome), [Catch](/docs/learn/catch)
<!-- sync:needs:end -->

::

Handling an error with `catch` is right when this function is the one that should decide what a failure means. Often it is not. The function is a step in the middle, and an error should simply become the caller's problem.

A `!` right after the call does exactly that. On success, `step!` is the value. On failure, the enclosing function fails with that same error at once, and nothing after the call runs.

## The long way

Written by hand, passing an error on is the same arm every time: catch the error and throw it again unchanged, `error => throw error`.

```rux
let high = ReadDigit(tens) catch { error => throw error };
let low = ReadDigit(units) catch { error => throw error };
```

`TwoDigitsByHand` writes that arm twice, once per digit. The two arms are near-identical and say nothing new.

## The same with !

`!` is that arm written once. The success values are used straight away, even in the middle of an expression:

```rux
func TwoDigits(tens: char, units: char) -> int ! DigitError {
    return ReadDigit(tens)! * 10 + ReadDigit(units)!;
}
```

`!` is tight, like any postfix operator, so it marks exactly one call. Every call that can fail needs its own.

```mermaid
flowchart LR
    step["`ReadDigit(tens)!`"] --> q{"Success or error?"}
    q -- "success" --> go["the expression is the digit;<br/>`TwoDigits` carries on"]
    q -- "error" --> out["`TwoDigits` fails at once<br/>with the same error"]
    out --> caller["the caller's `match`<br/>sees the original error"]
```

Both versions behave identically: `!` is shorthand, not a different rule. When both digits are wrong, only the first one is reported: the first `!` leaves, and the second read never happens.

## The error travels intact

Neither `TwoDigits` nor `!` looked at the error, yet the caller still learns which character was wrong:

```rux
.Failure(.NotADigit(c)) => PrintLine("'{}' is not a digit", c)
```

`Show` takes the reader as a function value, `read: func(char, char) -> int ! DigitError`, so it works with either version. That type can fail, so `read(tens, units)` gives back a fallible like any other call, and `Show` matches it by side: `value: int` for the success, and `.Failure(...)` with the error's own patterns.

## Two requirements

Passing an error on asks two things of the function doing it:

1. **It must be able to fail**, since that is where the error goes. `Main` returns a plain `int`, so `ReadDigit('4')!` there is rejected.
2. **The error must fit its own error.** Here both are `DigitError`, so it passes through as is. An error is never converted on the way: a different error type needs [Error mapping](/docs/learn/error-mapping), or an [error sum](/docs/learn/error-sum) that includes it.

| Tool                 | Who decides what an error means | The function                      |
| -------------------- | ------------------------------- | --------------------------------- |
| `F() catch { arms }` | this function, case by case     | can fail only if it declares so   |
| `F() !! fallback`    | this function, one answer       | can fail only if it declares so   |
| `F()!`               | the caller                      | can fail, with an error that fits |

## The program

The whole lesson is one package in the [Examples repository](https://github.com/rux-lang/Examples/tree/main/Errors/Propagate). Its comments explain every step.

<!-- sync:program:start -->

```rux [Src/Main.rux]
// Handling an error with `catch` is right when this function is the one that should decide what
// a failure means. Often it is not: the function is a step in the middle, and an error should
// simply become the caller's problem.
//
// Written by hand that is the same arm every time: catch the error and throw it again unchanged,
// `e => throw e`. A `!` right after the call is that arm written once. On success, `step!` is the
// value. On failure, the enclosing function fails with that same error at once, and nothing after
// the call runs.
//
// `!` is tight, like any postfix operator, so it marks exactly one call. Every call that can fail
// needs its own: `ReadDigit(tens)! * 10 + ReadDigit(units)!`.
import Io::PrintLine;

variant DigitError {
    Blank,
    NotADigit(char)
}

// One small step that can fail.
func ReadDigit(c: char) -> int ! DigitError {
    if c == ' ' {
        throw DigitError::Blank;
    }
    if c < '0' || c > '9' {
        throw DigitError::NotADigit(c);
    }
    return (c as int) - ('0' as int);
}

// The long way. Each error is caught only to be thrown straight back to the caller: two
// near-identical arms that say nothing new.
func TwoDigitsByHand(tens: char, units: char) -> int ! DigitError {
    let high = ReadDigit(tens) catch { error => throw error };
    let low = ReadDigit(units) catch { error => throw error };
    return high * 10 + low;
}

// The same function with `!`. The success values are used straight away, even in the middle of
// an expression.
func TwoDigits(tens: char, units: char) -> int ! DigitError {
    return ReadDigit(tens)! * 10 + ReadDigit(units)!;
}

// `read` is a function value whose type can fail, so its call gives back a fallible like any
// other, matched here by side.
func Show(read: func(char, char) -> int ! DigitError, tens: char, units: char) {
    match read(tens, units) {
        value: int => PrintLine("read {}", value),
        .Failure(.Blank) => PrintLine("a digit is missing"),
        .Failure(.NotADigit(c)) => PrintLine("'{}' is not a digit", c)
    }
}

func Main() -> int {
    Show(TwoDigits, '4', '2');
    Show(TwoDigits, '4', 'x');
    Show(TwoDigits, '?', '2');
    Show(TwoDigits, ' ', '7');

    // Both versions behave identically: `!` is shorthand, not a different rule.
    Show(TwoDigitsByHand, '4', 'x');

    // The error travels intact. Neither `TwoDigits` nor `!` looked at it, yet the caller still
    // learns which character was wrong.
    //
    // Passing an error on has two requirements. The function doing it must itself be able to
    // fail, since that is where the error goes. `Main` returns a plain `int`, so
    // `ReadDigit('4')!` is rejected here: "call to 'ReadDigit' can fail with 'DigitError', but
    // 'Main' cannot fail". And the error must fit that function's own error. Here both are
    // `DigitError`, so it passes through as is.
    return 0;
}
```

## Common mistakes

::mistake
**`!` in a function that cannot fail.**\
In `Main`, `let four = ReadDigit('4')!;` is an error:

```text
error: call to 'ReadDigit' can fail with 'DigitError', but 'Main' cannot fail
```

`Main` is always `func Main() -> int`, so it never passes an error on. Handle the error there with `!!` or `catch`, as [Exit status](/docs/learn/exit-status) shows.
::

::mistake
**Postfix ? on a call that can fail.**\
`return ReadDigit(tens)? * 10 + ReadDigit(units)?;` is refused, once for each `?`:

```text
error: '?' does not propagate errors
help: write '!' to pass the error on
```

`?` passes on an optional's absence, as in [Optional propagate](/docs/learn/optional-propagate). Errors are passed on with `!`.
::

::mistake
**Passing on an error of another type.**\
`!` never converts an error. In a function `Setting` declared `-> int ! SettingError`, `return ReadDigit(c)!;` is an error:

```text
error: call to 'ReadDigit' can fail with 'DigitError', but 'Setting' fails with 'SettingError'
note: an error passes on only as itself, as a member of a sum, or as part of a larger sum; it is never converted
help: handle the error with 'catch { ... }', or add 'DigitError' to the error of 'Setting'
```

[Error mapping](/docs/learn/error-mapping) and [Error sum](/docs/learn/error-sum) are the two fixes.
::

## Try it yourself

1. Add `Show(TwoDigits, ' ', 'x');` and predict which of the two messages it prints.
2. Write `ThreeDigits(hundreds: char, tens: char, units: char) -> int ! DigitError` with a `!` after each of three `ReadDigit` calls.
