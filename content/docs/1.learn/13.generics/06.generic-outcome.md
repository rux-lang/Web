# Generic outcome

::note
<!-- sync:needs:start -->

**You'll need**: [Generic](/docs/learn/generic), [Outcome](/docs/learn/outcome), [Catch fallback](/docs/learn/catch-fallback), [Optional propagate](/docs/learn/optional-propagate), [The is operator](/docs/learn/is)
<!-- sync:needs:end -->

::

Some questions get asked of outcomes again and again: "the value, or this fallback", "did it work?", "what went wrong, if anything?". For a struct you would answer them with methods. Optionals and fallible values are different: they are built into the language rather than declared by a package, so there is no package to own methods on them, and `extend` refuses them. The answer is a **generic function** whose parameter spells the form out — `T?` for an optional, `T ! E` for a fallible value — and which therefore works for every payload and every error type at once.

## Keeping an outcome

A call that can fail is usually handled where it is made. When its outcome has to be kept — stored, passed on, asked about later — the [fallible value](/docs/learn/outcome) itself is kept:

```rux
func Divide(numerator: int32, denominator: int32) -> int32 ! DivisionByZero {
    if denominator == 0 {
        throw DivisionByZero { numerator };
    }
    return numerator / denominator;
}
```

```rux
let even = Divide(12, 4);
let broken = Divide(7, 0);
```

Neither line passes an error on or handles one. `even` and `broken` both have the type `int32 ! DivisionByZero`: `even` holds the success 3, and `broken` holds a `DivisionByZero` error. From here on they are plain values, and the helpers below take them as arguments.

## A parameter that spells out the form

`ValueOr` takes any fallible value and a fallback of its success type:

```rux
// The success, or `fallback` when there is none. `!!` replaces an error with a value.
func ValueOr<T, E>(outcome: T ! E, fallback: T) -> T {
    return outcome !! fallback;
}
```

Nothing is written at the call. Given `even`, an `int32 ! DivisionByZero`, the compiler reads `T = int32` and `E = DivisionByZero` straight out of the argument's type, the way it read `T` out of a `Pair<T>` in [Generic type](/docs/learn/generic-type). The body is the [`!!` fallback](/docs/learn/catch-fallback) you already know; the only new thing is that it is written once for every success type and every error type there will ever be.

| Parameter written | Accepts                          | Helpers in this lesson                                   |
| ----------------- | -------------------------------- | -------------------------------------------------------- |
| `T ! E`           | any kept fallible value          | `Succeeded`, `Failed`, `ValueOr`, `SuccessOf`, `ErrorOf` |
| `T?`              | any optional                     | `Both`                                                   |
| `T?[..]`          | a slice of optionals of one type | `CountPresent`                                           |

## Which side, without taking it apart

`Succeeded` and `Failed` answer which side an outcome holds. [`is`](/docs/learn/is) only tests, so nothing is taken apart:

```rux
func Succeeded<T, E>(outcome: T ! E) -> bool {
    return outcome is .Success(_);
}

func Failed<T, E>(outcome: T ! E) -> bool {
    return outcome is .Failure(_);
}
```

`.Success(_)` and `.Failure(_)` are patterns that name the two sides of any fallible value, whatever its types are. That is what a generic body needs: inside `Failed`, the error type is only `E`, so a typed pattern such as `_: DivisionByZero` could not be written — but `.Failure(_)` can.

## Turning one form into another

Two small helpers move between the forms. `SuccessOf` keeps the success and forgets why there might not be one; `ErrorOf` keeps the other side:

```rux
// Keeps the success and forgets why there might not be one.
func SuccessOf<T, E>(outcome: T ! E) -> T? {
    return outcome !! none;
}

// The other side: the error, if there is one. `.Success` and `.Failure` name the sides whatever
// their types are, which is what a generic body needs.
func ErrorOf<T, E>(outcome: T ! E) -> E? {
    return match outcome {
        .Success(_) => none,
        .Failure(error) => error,
    };
}
```

`outcome !! none` replaces an error with absence, so a success becomes a present `T?` and a failure becomes `none`. In `ErrorOf`, the `.Failure` arm returns `error` as it is: a plain value converts to the optional on its own, so there is nothing to wrap it in.

```mermaid
flowchart LR
    f(["`T ! E`"]) -- "`SuccessOf`" --> s(["`T?`"])
    f -- "`ErrorOf`" --> e(["`E?`"])
    f -- "`ValueOr(fallback)`" --> t(["`T`"])
    f -- "`Succeeded` / `Failed`" --> b(["`bool`"])
```

`ErrorOf(broken)` is a `DivisionByZero?`, so `Main` can open it with an `error?` pattern from [Presence](/docs/learn/presence) and read the error's own field:

```rux
match ErrorOf(broken) {
    error? => PrintLine("ErrorOf      cannot divide {} by zero", error.numerator),
    none => PrintLine("ErrorOf      nothing went wrong"),
}
```

## Optionals too

`Both` combines two optionals of possibly different types. The postfix `?` from [Optional propagate](/docs/learn/optional-propagate) does the work: if either is `none`, the function returns `none` on the spot.

```rux
func Both<T, U>(first: T?, second: U?) -> (T, U)? {
    return (first?, second?);
}
```

And a helper can take a whole slice of optionals. `T?[..]` is a slice of `T?`, so an `int32?[4]` array is passed straight to it, and a comparison with `none` asks whether each one holds a value:

```rux
func CountPresent<T>(values: T?[..]) -> uint {
    var count: uint = 0;
    for value in values {
        if value != none {
            count++;
        }
    }
    return count;
}
```

## A kept outcome is given away

Inside these helpers `T` and `E` might be anything, including types that own memory, so a `T ! E` parameter is treated as an owning value, as every generic `T` is in [Generic bound](/docs/learn/generic-bound). `outcome !! fallback` and `match outcome` take the outcome, and that is fine: each helper uses its parameter once. A helper that wants to test an outcome and then hand it back has to test it with `is`, which takes nothing — calling `Succeeded(first)` first would give `first` away to `Succeeded`.

## The program

The whole lesson is one package in the [Examples repository](https://github.com/rux-lang/Examples/tree/main/Generics/GenericOutcome). Its comments explain every step.

<!-- sync:program:start -->

```rux [Src/Main.rux]
// Optionals and fallible values are built into the language rather than declared by a package, so
// there is no package to own methods on them. `extend int32? { ... }` is rejected: "cannot extend
// native type 'int32?'". A question you keep asking of an optional is written instead as a
// generic function whose parameter spells the form out: `T?`.
//
// The same style serves an outcome kept as a value. A call that can fail is usually handled where
// it is made, but when its outcome has to be kept, the fallible value itself is kept:
// `let even = Divide(12, 4);` holds an `int32 ! DivisionByZero`, a success or an error. A helper
// over `T ! E` works for every success type and every error type at once, and nothing needs to be
// written at the call: `T` and `E` are read straight out of the argument's type.
import Io::PrintLine;

struct DivisionByZero {
    numerator: int32;
}

func Divide(numerator: int32, denominator: int32) -> int32 ! DivisionByZero {
    if denominator == 0 {
        throw DivisionByZero { numerator };
    }
    return numerator / denominator;
}

// Which side an outcome holds, without taking it apart. `is` only asks, so nothing is taken.
func Succeeded<T, E>(outcome: T ! E) -> bool {
    return outcome is .Success(_);
}

func Failed<T, E>(outcome: T ! E) -> bool {
    return outcome is .Failure(_);
}

// The success, or `fallback` when there is none. `!!` replaces an error with a value.
func ValueOr<T, E>(outcome: T ! E, fallback: T) -> T {
    return outcome !! fallback;
}

// Keeps the success and forgets why there might not be one.
func SuccessOf<T, E>(outcome: T ! E) -> T? {
    return outcome !! none;
}

// The other side: the error, if there is one. `.Success` and `.Failure` name the sides whatever
// their types are, which is what a generic body needs.
func ErrorOf<T, E>(outcome: T ! E) -> E? {
    return match outcome {
        .Success(_) => none,
        .Failure(error) => error,
    };
}

// Optionals too: both values when both are present, and nothing otherwise.
func Both<T, U>(first: T?, second: U?) -> (T, U)? {
    return (first?, second?);
}

// And a whole array of them: an `int32?[4]` is passed straight to the `T?[..]` slice.
func CountPresent<T>(values: T?[..]) -> uint {
    var count: uint = 0;
    for value in values {
        if value != none {
            count++;
        }
    }
    return count;
}

func Main() -> int {
    let even = Divide(12, 4);
    let broken = Divide(7, 0);
    PrintLine("ValueOr      {} {}", ValueOr(even, -1), ValueOr(broken, -1));
    PrintLine("Succeeded    {} {}", Succeeded(even), Succeeded(broken));
    PrintLine("Failed       {} {}", Failed(even), Failed(broken));
    PrintLine("SuccessOf    {}", SuccessOf(even) ?? 0);

    match ErrorOf(broken) {
        error? => PrintLine("ErrorOf      cannot divide {} by zero", error.numerator),
        none => PrintLine("ErrorOf      nothing went wrong"),
    }

    let width: int32? = 80;
    let height: int32? = 24;
    let missing: char8[..]? = none;
    match Both(width, height) {
        size? => PrintLine("Both         {} x {}", size.0, size.1),
        none => PrintLine("Both         incomplete"),
    }
    PrintLine("Both         complete: {}", Both(width, missing) != none);

    let readings: int32?[4] = [3, none, 5, none];
    PrintLine("CountPresent {} of {}", CountPresent(readings), readings.length);
    return 0;
}
```

## Common mistakes

::mistake
**Trying to extend an optional.**\
`extend int32? { … }` fails with:

```text
error: cannot extend native type 'int32?'
  note: a sum, optional, or unit type has no declaring package to own methods or interface implementations
  help: write a generic function that takes the native type as a parameter
```

The help gives this lesson's answer.
::

::mistake
**Passing a plain value where a fallible one is expected.**\
`ValueOr(12, -1)` fails with:

```text
error: function 'ValueOr' requires 2 type arguments, but 0 were provided
```

A plain `int` has no error type, so there is nothing to read `E` from. A value converts to a fallible one only when the error type is known — `ValueOr<int32, DivisionByZero>(12, -1)` is accepted.
::

::mistake
**Using a kept outcome as its success.**\
`even + 1` fails with:

```text
error: operator '+' cannot combine left operand 'int32 ! DivisionByZero' with right operand 'int'
  help: pass the error on with '!', replace it with '!!', or handle it with 'catch { ... }'
```

`even` might hold an error. Take the success out first — `ValueOr(even, 0) + 1`, or `(even !! 0) + 1`.
::

::mistake
**Wrapping a present value.**\
Write the `ErrorOf` arm as `.Failure(error) => .Some(error)` and it fails with:

```text
error: an optional has no case '.Some'
  help: write the value itself, which converts to the optional
```

`error` converts to `E?` by itself. In a pattern, a present value is matched with `error?`, not `.Some(error)`.
::

## Try it yourself

1. Write `OrElse<T>(value: T?, fallback: T) -> T` with `??`, and call it with an `int32?` and a `char8[..]?`.
2. Write `IsPresent<T>(value: T?) -> bool`, then rewrite `CountPresent` to use it.
3. Write `Either<T, E>(first: T ! E, second: T ! E) -> T ! E` that returns `first` if it succeeded and `second` otherwise. Test `first` with `is`; then try `Succeeded(first)` in its place and read the error.
4. Keep the outcome of a fallible function from an earlier lesson and pass it to `ValueOr`. Did you have to change `ValueOr`?
