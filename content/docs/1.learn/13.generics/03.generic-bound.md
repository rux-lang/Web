# Generic bound

::note
<!-- sync:needs:start -->

**You'll need**: [Generic](/docs/learn/generic), [Interface](/docs/learn/interface), [Extension](/docs/learn/extension)
<!-- sync:needs:end -->

::

An unconstrained `<T>` promises nothing about `T`. The body may store a `T`, pass it on and hand it back, but it cannot call a method on it, because nothing says the method exists. A **bound** makes that promise. `<T: Scored>` accepts only types that implement the interface `Scored`, and in return the body may call `Scored`'s methods on any `T`. It is the generic counterpart of the [Interface](/docs/learn/interface) lesson: the same interface, used to choose which types may come in.

## A bound is written after a colon

Here is the interface, and one type that implements it:

```rux
interface Scored {
    func Score() -> int32;
}

extend Player : Scored {
    func Score(&self) -> int32 {
        return self.points;
    }
}
```

`Best` names the interface after its type parameter:

```rux
func Best<T: Scored>(first: T, second: T) -> T {
    if second.Score() > first.Score() {
        return second;
    }
    return first;
}
```

`Score` is callable on `first` and `second` only because of the bound. Remove `: Scored` and the body itself is rejected — not a particular call, the definition — because a plain `T` has no `Score`.

The winner comes back as a `T`. Called with two `Player` values, `Best` returns a `Player`, so `winner.name` and `winner.points` are right there; it never turns into "some `Scored`".

## The check happens at the call

```mermaid
flowchart LR
    invoke["`Best(ana, bo)`"] --> t["`T = Player`"]
    t --> q{"Does `Player`<br/>implement `Scored`?"}
    q -- "yes" --> inst["`Best` is compiled for `Player`;<br/>`Score()` calls `Player`'s `Score`"]
    q -- "no" --> err["error at the call:<br/>`type argument … does not satisfy`<br/>`interface bound 'Scored'`"]
```

The compiler works out `T` from the arguments first, then checks the bound. A type without an implementation is rejected where it is passed in, with a note naming the method it is missing — never somewhere deep inside the body. That makes the bound a contract you can read from the signature alone: anything `Scored` may be passed, and nothing else.

## Primitives qualify only through an implementation

`int32` has no `Score` until something gives it one. An `extend` block on a primitive does, and from then on a bare number is its own score:

```rux
extend int32 : Scored {
    func Score(&self) -> int32 {
        return self;
    }
}
```

Note the call in `Main`:

```rux
PrintLine("best number  {}", Best<int32>(3, 9));
```

The `<int32>` matters. Two unsuffixed literals make `T` an `int` (the [Literal](/docs/learn/literal) rule), and `int` is a different type from `int32`, one that nothing has made `Scored`. Writing `T` out turns `3` and `9` into `int32` values.

## A bound travels

`Margin` has a bound of its own, and that is what lets it call `Best`:

```rux
func Margin<T: Scored>(first: T, second: T) -> int32 {
    let total = first.Score() + second.Score();
    let winner = Best(first, second);
    return winner.Score() * 2 - total;
}
```

Inside `Margin`, `T` is known only to be `Scored`. That is exactly what `Best` requires, so the call is accepted. A generic that calls another generic must promise at least what the callee demands.

## A T might own something

Notice the order inside `Margin`: both scores are asked for _before_ `Best` is called. That is not style; it is required.

The body of `Margin` is checked once, for every `T` at once, and it cannot know whether the `T` it gets is plain data like `Player` or a value that owns memory, like a [`String`](/docs/learn/string). So it treats every `T` as a value that might own something. Passing `first` to `Best` gives it away, exactly as passing an owning value does in [Give away](/docs/learn/give-away), and after that `first` cannot be used. Ask for `first.Score()` on the last line instead and the compiler refuses it.

A method call is different: it only lends its receiver, so `first.Score()` gives nothing away, and the scores can be read as often as you like before the call.

| In a generic body     | What happens to the `T`          |
| --------------------- | -------------------------------- |
| `first.Score()`       | lent to the method, still usable |
| `Best(first, second)` | given away, unusable afterwards  |
| `return first;`       | given away to the caller         |

None of this applies to `Main`. There `T` is `Player`, a struct of a slice and an `int32` (plain data), so `Best(ana, bo)` copies both players, and `Margin(ana, bo)` can take them again on the next line.

A bound can also ask for the other kind of `T`. `Copyable`, from `Core::Ownership`, admits only plain data, and a `T: Scored + Copyable` is copied rather than given away, so it may be used any number of times. [Multiple bounds](/docs/learn/multiple-bounds) shows how to write two bounds at once.

## A bound costs nothing at run time

A bound and an [interface view](/docs/learn/interface-value) both use an interface, but they work differently:

|                         | Bound: `<T: Scored>`                             | Interface view: `&Scored`                     |
| ----------------------- | ------------------------------------------------ | --------------------------------------------- |
| Which type?             | one concrete type per call, fixed when compiling | any implementing type, decided while running  |
| Method call             | direct, as if written for that type              | looked up through the view at run time        |
| What comes back         | the same `T` that went in: a `Player`            | a `Scored`; the `Player` is no longer visible |
| Mixed types in one call | no: `first` and `second` are both `T`            | yes                                           |

Each instantiation calls its own type's method directly, as if `Best` had been written out by hand for `Player` and again for `int32`.

## The program

The whole lesson is one package in the [Examples repository](https://github.com/rux-lang/Examples/tree/main/Generics/GenericBound). Its comments explain every step.

<!-- sync:program:start -->

```rux [Src/Main.rux]
// An unconstrained `<T>` promises nothing about `T`, so a generic body can only pass a `T`
// around. A bound changes that: `<T: Scored>` accepts only types that implement `Scored`, and
// in return the body may call `Scored`'s methods on any `T`.
//
// The check happens at the call. A type without an implementation is rejected where it is
// passed in, with a note naming the method it is missing, never somewhere deep in the body.
//
// Unlike an interface value, a bound costs nothing at run time. Each instantiation calls its
// own type's method directly, as if the function had been written out by hand for that type.
import Io::PrintLine;

interface Scored {
    func Score() -> int32;
}

struct Player {
    name: char8[..];
    points: int32;
}

extend Player : Scored {
    func Score(&self) -> int32 {
        return self.points;
    }
}

// Primitives satisfy a bound the same way: only through an implementation. `int32` has no
// `Score` until this block gives it one, and then a bare number is its own score.
extend int32 : Scored {
    func Score(&self) -> int32 {
        return self;
    }
}

// `Score` is callable on `first` and `second` only because of the bound. The winner is handed
// back as a `T`, so a `Player` comes back as a `Player`, not as a `Scored`.
func Best<T: Scored>(first: T, second: T) -> T {
    if second.Score() > first.Score() {
        return second;
    }
    return first;
}

// How far the winner leads. A bound travels: a `T` that is `Scored` here satisfies `Best` too.
//
// The body cannot know whether `T` owns resources, so it treats every `T` as a value that might:
// passing `first` to `Best` gives it away, and the scores are asked for before that. Ask after,
// and `first.Score()` is refused:
//
// error: 'first' is used after it was given away
//   note: 'first' was given away at 58:23
//   help: lend it with '&first' where it is only read, or clone it where both uses need a value
//
// A method call only lends its receiver, so `first.Score()` gives nothing away. A `T` bounded by
// `Copyable`, from `Core::Ownership`, is copied instead and may be used any number of times; the
// bound then admits only plain data, such as `Player` and `int32` here.
func Margin<T: Scored>(first: T, second: T) -> int32 {
    let total = first.Score() + second.Score();
    let winner = Best(first, second);
    return winner.Score() * 2 - total;
}

func Main() -> int {
    let ana = Player { name: "Ana", points: 12 };
    let bo = Player { name: "Bo", points: 17 };
    let winner = Best(ana, bo);
    PrintLine("best player  {} with {}", winner.name, winner.points);
    PrintLine("margin       {}", Margin(ana, bo));

    // An unsuffixed literal is an `int`, which has no `Score`, so the type is written out.
    PrintLine("best number  {}", Best<int32>(3, 9));

    // `Best(2.5, 1.5)` is rejected: "type argument 'float64' does not satisfy interface bound
    // 'Scored' on type parameter 'T'", with a note that 'Scored' requires method 'Score'. A
    // `float64` can be compared with `>`, but nothing has made it `Scored`.
    return 0;
}
```

## Common mistakes

::mistake
**Calling a method on an unbound `T`.**\
Without the bound, `second.Score()` fails with:

```text
error: no interface bound on type parameter 'T' provides method 'Score'
  help: add a bound whose interface declares 'Score', as in 'T: SomeInterface'
```

The definition is rejected, not a particular call.

::

::mistake
**Passing a type that is not `Scored`.**\
`Best(2.5, 1.5)` fails with an error and a note:

```text
error: type argument 'float64' does not satisfy interface bound 'Scored' on type parameter 'T'
  note: interface 'Scored' requires method 'Score', which type 'float64' does not implement
```

A `float64` can be compared with `>`, but nothing has made it `Scored`.
::

::mistake
**Bare literals become `int`, not `int32`.**\
`Best(3, 9)` fails the same way, naming `'int'`: the literals have no typed partner, so `T` is `int`, and only `int32` was given a `Score`. Write `Best<int32>(3, 9)`, or pass `int32` variables.
::

::mistake
**Using a `T` after giving it away.**\
Read the scores after the call, `return winner.Score() * 2 - first.Score() - second.Score();`, and `Margin` fails with:

```text
error: 'first' is used after it was given away
  note: 'first' was given away at 59:23
  help: lend it with '&first' where it is only read, or clone it where both uses need a value
```

`Best(first, second)` took both values. Ask for what you need before handing a `T` on, as `Margin` does with `total`.
::

::mistake
**Calling a bounded generic from an unbounded one.**\
If `Margin` were `<T>` without the bound, its call `Best(first, second)` would fail with:

```text
error: type argument 'T' does not satisfy interface bound 'Scored' on type parameter 'T'
  help: add the bound to the enclosing declaration, as in 'T: Scored'
```

Its own `first.Score()` calls would fail too, with the error from the first mistake above.
::

## Try it yourself

1. Add a third player and write `BestOfThree<T: Scored>(a: T, b: T, c: T) -> T` using `Best` twice. Can you pass `a` to `Best` and then use it again?
2. Implement `Scored` for `float64` (perhaps the value rounded down with `as int32`) and make `Best(2.5, 1.5)` compile.
3. Declare a `struct Team` with a `wins` field, implement `Scored` for it, and pass two teams to `Margin`. Nothing in `Margin` or `Best` changes.
4. Try `Best(ana, 9)`. Why is a `Player` and an `int32` rejected, even though both are `Scored`?
