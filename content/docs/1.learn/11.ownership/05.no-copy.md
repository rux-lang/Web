# Non-copyable types

::note
<!-- sync:needs:start -->

**You'll need**: [Destructor](/docs/learn/destructor), [Move](/docs/learn/move)
<!-- sync:needs:end -->

::

A hotel key stands for a room. The key itself is plain data — a room number — so the compiler would happily [copy](/docs/learn/copy) it, and then two guests could each check out of the same room. For a type like this the automatic copy is wrong, and Rux lets the type turn it off.

Once copying is off, the only way to hand a key on is to [move](/docs/learn/move) it. One key, one owner, one checkout — and the compiler checks all three.

## Turning copying off

The attribute `#NoCopy` on the declaration says "this type has no copy":

```rux
#NoCopy
struct RoomKey {
    room: int32;
}
```

That is all. `RoomKey` keeps its one `int32` field and needs no `extend` block; it simply stops being copyable.

A type with a [destructor](/docs/learn/destructor) needs no attribute: it owns something, so it is already move-only. `#NoCopy` is for plain data that must still never be duplicated, such as a handle that something else releases. Its sibling `#NoMove` goes further and keeps a value in the place where it was built.

## Moving instead

From then on every use that would copy a key is an error, and the diagnostic shows the move to write instead:

```rux
let spare = key;
```

```
error: cannot copy 'RoomKey', which prohibits copying
  note: a named value used by value in initialization position is copied, and only plain data copies
  help: write 'move key' to transfer it
```

With `move`, the key changes hands and `key` is finished:

```rux
let friend = move key;
PrintLine("    friend holds key {}", friend.room);
```

Passing by value is a copy too, so an argument needs `move` as well. `CheckOut` takes ownership of the key, so after the call nobody holds it any more:

```rux
func CheckOut(key: RoomKey) {
    PrintLine("    checking out of room {}", key.room);
    PrintLine("    key {} handed back", key.room);
}
```

```rux
CheckOut(move friend);
PrintLine("    done");
```

## Fresh keys and borrowed keys

Two things still work without `move`. A value made on the spot has no old owner, so `CheckIn` returns its new key with a plain `return`, and `Main` takes it with a plain `=`:

```rux
func CheckIn(room: int32) -> RoomKey {
    PrintLine("    key {} issued", room);
    return RoomKey { room: room };
}
```

```rux
let key = CheckIn(12);
```

And a borrow is not a copy. A function that only needs to look at a key takes `&RoomKey`, and the caller keeps the key.

```mermaid
flowchart LR
    k(["`key: RoomKey`<br/>`#NoCopy`"]) -- "`let spare = key`" --> x["`error: cannot copy`<br/>`'RoomKey'`"]
    k -- "`let friend = move key`" --> f["`friend` owns the key<br/>`key` is finished"]
    k -- "`Peek(key)` with `key: &RoomKey`" --> b["borrowed for the call<br/>`key` still owns it"]
```

## Everywhere a copy would happen

Every by-value use of a named key needs `move`. The compiler's note names the place in each error — initialization, argument, return or assignment position:

| Where          | Refused                | Written with a move         |
| -------------- | ---------------------- | --------------------------- |
| A binding      | `let spare = key;`     | `let spare = move key;`     |
| An argument    | `CheckOut(key)`        | `CheckOut(move key)`        |
| A return       | `return key;`          | `return move key;`          |
| A struct field | `Booking { key: key }` | `Booking { key: move key }` |
| An assignment  | `key = other;`         | `key = move other;`         |

The prohibition also spreads outwards. A struct with a `RoomKey` field cannot be copied either — copying it would copy the key — so the compiler treats the whole struct as move-only, and `let copy = booking;` is refused with `cannot copy 'Booking', which prohibits copying`.

## The program

The whole lesson is one package in the [Examples repository](https://github.com/rux-lang/Examples/tree/main/Ownership/NoCopy). Its comments explain every step.

<!-- sync:program:start -->

```rux [Src/Main.rux]
// A hotel key stands for a room. The key itself is plain data, a room number, so the compiler
// would happily copy it, and then two guests could each check out of the same room. For a type
// like this the automatic copy is wrong, and Rux lets the type turn it off.
//
// The attribute `#NoCopy` on the declaration says "this type has no copy":
//
//     #NoCopy
//     struct RoomKey { room: int32; }
//
// From then on every use that would copy a key is an error, and the only way to hand one on is
// to move it with `move`. One key, one owner, one checkout.
//
// A type with a destructor needs no attribute: it owns resources, so it is already move-only, as
// Destructor showed. `#NoCopy` is for plain data that must still never be duplicated, such as a
// handle that something else releases. (Its sibling `#NoMove` goes further and keeps a value
// where it was built.)
import Io::PrintLine;

#NoCopy
struct RoomKey {
    room: int32;
}

func CheckIn(room: int32) -> RoomKey {
    PrintLine("    key {} issued", room);
    return RoomKey { room: room };
}

// Takes ownership of the key, so after this call nobody holds it any more.
func CheckOut(key: RoomKey) {
    PrintLine("    checking out of room {}", key.room);
    PrintLine("    key {} handed back", key.room);
}

func Main() -> int {
    PrintLine("check in:");
    let key = CheckIn(12);

    // A copy is refused, and the diagnostic shows the move to write instead:
    //
    //     let spare = key;
    //
    // error: cannot copy 'RoomKey', which prohibits copying
    //   note: a named value used by value in initialization position is copied, and only plain
    //         data copies
    //   help: write 'move key' to transfer it

    PrintLine("give the key to a friend:");
    let friend = move key;
    PrintLine("    friend holds key {}", friend.room);

    // Passing by value is a copy too, so the argument needs `move` as well. Without it:
    //
    //     error: cannot copy 'RoomKey', which prohibits copying
    //       help: write 'move friend' to transfer it
    PrintLine("check out:");
    CheckOut(move friend);
    PrintLine("    done");
    return 0;
}
```

## Common mistakes

::mistake
**Binding or passing a key without `move`.**\
`let spare = key;` and `CheckOut(friend)` both fail with:

```text
error: cannot copy 'RoomKey', which prohibits copying
```

The notes name the place — initialization position, argument position — and the help writes the `move` for you: `write 'move key' to transfer it`.
::

::mistake
**Returning a named key with a plain `return`.**\
A function that builds a key in a local and ends with `return key;` fails the same way, in return position:

```text
error: cannot copy 'RoomKey', which prohibits copying
  note: a named value used by value in return position is copied, and only plain data copies
  help: write 'move key' to transfer it
```

Write `return move key;`. Only a value made on the spot, like `return RoomKey { room: room };`, needs no `move`.
::

::mistake
**Turning copying off with a bodyless `=`.**\
Declaring `func =(&var self, other: &RoomKey);` in `extend RoomKey`, without the attribute, does not prohibit anything:

```text
error: a bodyless 'func =' does not prohibit copying
  help: mark 'RoomKey' with '#NoCopy' instead
```

The attribute is the only spelling, and like every attribute without arguments it takes no parentheses — `#NoCopy()` is refused too.
::

## Try it yourself

1. Write `func Peek(key: &RoomKey)` that prints the room number, and call it twice on `key` before giving it to the friend. Why does `Peek` need no `move`?
2. Write `func Spare(room: int32) -> RoomKey` that stores a new key in a `let` before returning it. Which `return` does it need?
3. Make two `var` keys and replace the first with `first = move second;`. Can `second` still be read afterwards?
4. Declare `struct Booking { guest: char8[..]; key: RoomKey; }`, build one, and try to copy it with `=`. What does the error say about `Booking`?
