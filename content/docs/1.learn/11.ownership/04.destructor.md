# Destructor

::note
<!-- sync:needs:start -->

**You'll need**: [Give away](/docs/learn/give-away), [Method](/docs/learn/method)
<!-- sync:needs:end -->

::

A _destructor_ is code that runs when a value's life ends. Nobody calls it. The compiler does, exactly once for every value that is still alive when its life ends — when its scope closes, when a function returns, or when `=` replaces it with a new value.

In real code a destructor gives back what the value was holding: a file, a network connection, a block of memory. Because the compiler calls it, it cannot be forgotten, and it cannot be called twice. Here the destructor only prints, so that you can watch exactly when it runs.

## Writing a destructor

A destructor is written inside `extend`, as a block with no name and no parameters:

```rux
struct Guest {
    name: char8[..];
}

extend Guest {
    destructor {
        PrintLine("    {} leaves", self.name);
    }
}
```

Inside it, `self` is a `&var` loan of the dying value, so the destructor can read every field and change one on the way out — close a handle, clear a pointer. The form is fixed:

- no parameter list and no result type,
- no `pub` — it runs wherever a value of the type ends, in any package,
- at most one per type.

## When a scope ends

The guest in `Visit` lives only as long as the call:

```rux
func Visit(name: char8[..]) {
    let guest = Guest { name: name };
    PrintLine("    {} visits", guest.name);
}
```

```text
a short visit:
    Ada visits
    Ada leaves
    back in Main
```

"Ada leaves" is printed by the destructor as `Visit` returns, before `Main` carries on. The same happens at the end of every block that owns a value — including each pass of a loop body.

## When a value is replaced

Replacing a value ends the old one's life first:

```rux
var seat = Guest { name: "Bob" };
seat = Guest { name: "Cy" };
```

Bob leaves at the `=`. Cy now holds the seat and will leave later. Replacing one field of a struct works the same way: the old field value is destroyed, and the rest of the struct is untouched.

## When a value is given away

After a value is [given away](/docs/learn/give-away), only the new owner destroys it:

```rux
let host = Guest { name: "Dee" };
let moved = host;
```

`host` gave its value away, so there is nothing left in `host` to destroy. Dee leaves once, at the end of `Main`, as `moved`.

## Newest first

Values that end together are destroyed in reverse order of creation — newest first. At the end of `Main`, `seat` (holding Cy) was created before `moved` (holding Dee), so Dee leaves first:

```mermaid
flowchart LR
    subgraph made["Created, in order"]
        direction LR
        c1["`seat`: Cy"] --> c2["`moved`: Dee"]
    end
    subgraph gone["Destroyed at the end of `Main`"]
        direction LR
        d1["Dee leaves"] --> d2["Cy leaves"]
    end
    made -- "reversed" --> gone
```

The order is not arbitrary. A value made later may depend on one made earlier — a reader that uses an open file, say — so it has to go first, while the thing it depends on is still there.

| What happens               | Destructor runs                            |
| -------------------------- | ------------------------------------------ |
| The owning scope ends      | yes, newest value first                    |
| `=` replaces the value     | yes, on the old value, at the assignment   |
| The value is given away    | not here — the new owner destroys it later |
| The value is used by value | never copied — it is given away instead    |

## A type with a destructor is never copied

A [copy](/docs/learn/copy) of a guest would be a second guest, and it would leave too — "Dee leaves" printed twice for one person. For a guest that only prints, that is odd; for a value that frees memory or closes a file, it would free or close the same thing twice. So a type with a destructor owns something, and the compiler never copies it: `let moved = host;` gives the guest away, and `host` is finished. A later read of `host` is refused:

```text
error: 'host' is used after it was given away
  help: lend it with '&host' where it is only read, or clone it where both uses need a value
```

For the same reason, a function that only reads a guest is handed a written loan, `&host`, even where a plain-data value could go bare — the rule [Exclusivity](/docs/learn/exclusivity) set out. The [Non-copyable types](/docs/learn/no-copy) lesson turns copying off for plain data that has no destructor, and [Custom copy](/docs/learn/custom-copy) writes the `Clone` method that the help mentions. To end a guest's stay _before_ its scope closes, the [next lesson](/docs/learn/destroy) uses `destroy`.

## The program

The whole lesson is one package in the [Examples repository](https://github.com/rux-lang/Examples/tree/main/Ownership/Destructor). Its comments explain every step.

<!-- sync:program:start -->

```rux [Src/Main.rux]
// A destructor is code that runs when a value's life ends. It is written inside `extend` as a
// block with no name and no parameters, and `self` in it is a `&var` loan of the dying value:
//
//     destructor { ... }
//
// Nobody calls it. The compiler does, exactly once for every value that is still alive when its
// life ends: when its scope closes, when a function returns, or when `=` replaces it with a new
// value, whether it is a whole variable or one field of a struct. A value that was given away is
// not destroyed where it was, because its new owner will destroy it later. Values that end
// together are destroyed in reverse order of creation, newest first.
//
// Here the destructor only prints, so its timing can be watched. In real code it gives back what
// the value was holding: a file, a connection, a block of memory. A copy would be a second guest
// that leaves too, so a type with a destructor is never copied: `let other = guest;` gives the
// guest away, as GiveAway showed, and `guest` is finished.
import Io::PrintLine;

struct Guest {
    name: char8[..];
}

extend Guest {
    destructor {
        PrintLine("    {} leaves", self.name);
    }
}

// The guest lives only as long as this call.
func Visit(name: char8[..]) {
    let guest = Guest { name: name };
    PrintLine("    {} visits", guest.name);
}

func Main() -> int {
    PrintLine("a short visit:");
    Visit("Ada");
    PrintLine("    back in Main");

    // Replacing a value ends the old one's life first.
    PrintLine("swapping the seat:");
    var seat = Guest { name: "Bob" };
    seat = Guest { name: "Cy" };

    // Given away, only the new owner is destroyed, so Dee leaves once, at the end.
    PrintLine("giving away:");
    let host = Guest { name: "Dee" };
    let moved = host;

    // `moved` was created after `seat`, so it is destroyed before it.
    PrintLine("end of Main:");
    return 0;
}
```

## Common mistakes

::mistake
**Writing a destructor as a function.**\
`func ~Guest(&var self) { … }` inside `extend Guest` fails with:

```text
error: a destructor is not a function
  help: write 'destructor { ... }'
```

A destructor has no name, no parameters and no result, and nothing calls it by name. Write the block on its own: `destructor { … }`.
::

::mistake
**Two destructors for one type.**\
A second `destructor { … }` for `Guest`, in the same `extend` block or another, fails with:

```text
error: 'Guest' already has a destructor
  help: merge the two bodies into one 'destructor { ... }'
```

A value ends once, so its type has one place to say what happens then.
::

::mistake
**Letting an error leave a destructor.**\
A call such as `Check(self.owed)!;` inside a destructor, which passes a failure on, fails with:

```text
error: an error cannot leave a destructor
  help: handle it with '!!' or 'catch { ... }'
```

The value is already being destroyed, and there is nobody to hand the error to. Handle it inside the destructor — or end the value with a method that can fail, as the [next lesson](/docs/learn/destroy) does.
::

::mistake
**Expecting a copy.**\
`let twin = host;` does not copy a guest — it gives the guest away, so a later `host.name` fails with:

```text
error: 'host' is used after it was given away
```

Two guests would leave for one person. Lend the guest with `&host` where it is only read, or give `Guest` a `Clone` method, as in [Custom copy](/docs/learn/custom-copy), when a second guest is really wanted.
::

## Try it yourself

1. Create a guest inside a `for` loop over `0..3` and print the pass number. When does each guest leave?
2. Add `PrintLine("{}", host.name);` after `let moved = host;` and read the error. Then print `moved.name` instead.
3. Declare `struct Table { number: int32; guest: Guest; }`, make a `var` table, and assign a new guest to its `guest` field. Who leaves, and when?
