# Destroy

::note
<!-- sync:needs:start -->

**You'll need**: [Destructor](/docs/learn/destructor), [Give away](/docs/learn/give-away), [Unit fallible](/docs/learn/unit-fallible), [Catch](/docs/learn/catch)
<!-- sync:needs:end -->

::

The [Destructor](/docs/learn/destructor) lesson showed when a value's life ends: at the end of its scope, at a return, or when `=` replaces it. There are two things a destructor cannot do. It cannot run sooner than that, and it cannot report a problem, because no error may leave a destructor.

This lesson covers the two ways around both. `destroy value;` ends a value **now**, on the line you choose. And a method whose receiver is `~self` ends the value **instead of** its destructor — a method you name and call, which can hand back part of the value or fail.

## A hotel stay

A stay holds a room key, and both clean up after themselves. The key goes back to the desk in its own destructor:

```rux
struct Key {
    room: int32;
}

extend Key {
    destructor {
        PrintLine("    key {} back at the desk", self.room);
    }
}
```

A stay has a guest, a key and an open bill:

```rux
struct Stay {
    guest: char8[..];
    key: Key;
    owed: int32;
}
```

Its destructor, in `extend Stay`, is the end nobody chose — the hotel closes the stay:

```rux
// The end nobody chose: the hotel closes the stay.
destructor {
    PrintLine("    the hotel closes {}'s stay", self.guest);
}
```

## Ending a value now

`destroy` ends a value on the spot:

```rux
let early = Stay { guest: "Ada", key: Key { room: 1 }, owed: 0 };
destroy early;
PrintLine("    Ada's stay is over");
```

```text
destroy:
    the hotel closes Ada's stay
    key 1 back at the desk
    Ada's stay is over
```

The value is destroyed exactly as it would have been at the end of `Main` — just earlier. The stay's destructor runs first, then its fields, last declared first, so the key goes back to the desk after the hotel has closed the stay. Ada is not destroyed a second time where `Main` ends.

From the `destroy` on, the name is finished, as after giving the value away:

```text
error: 'early' is used after it was destroyed
  note: 'early' was destroyed with 'destroy' at 65:5
```

`destroy` ends a whole value that has a name — a local, or a parameter the function took by value. It ends plain data too: nothing runs, but the name is finished all the same.

| `destroy` on…                     | What happens                                  |
| --------------------------------- | --------------------------------------------- |
| a local or a by-value parameter   | destructor, then fields; the name is finished |
| a field or an element of a value  | refused — assign it a new value instead       |
| a value reached through a loan    | refused — the owner ends it, not the borrower |
| a temporary, such as `Stay { … }` | refused — its statement destroys it already   |

## Ending a value with a method

A guest who checks out ends the stay on purpose. `CheckOut` takes its receiver as `~self`:

```rux
// Ends the stay in place of the destructor, and fails while the bill is open. Either way the
// stay is over and the key, still a field, is destroyed when the method leaves.
func CheckOut(~self) -> !Unpaid {
    if self.owed > 0 {
        throw Unpaid { owed: self.owed };
    }
    PrintLine("    {} checks out", self.guest);
}
```

A `~self` method is an _ending method_. The call takes the value, as a by-value `self` would, and the caller's name is finished afterwards. The destructor does **not** run: the method takes its place. Inside, every field of `self` is a local of its own, and the fields still there when the method leaves — by its last line, a `return` or a `throw` — are destroyed, last declared first.

Bob has paid, so his stay ends cleanly:

```rux
let paid = Stay { guest: "Bob", key: Key { room: 2 }, owed: 0 };
paid.CheckOut() catch {
    e => {
        PrintLine("    {} still to pay", e.owed);
    }
};
```

```text
check out:
    Bob checks out
    key 2 back at the desk
```

There is no "the hotel closes Bob's stay" line. The method replaced the destructor, and only the key, a field, was destroyed after its body.

## An ending that fails

Unlike a destructor, an ending method can fail and say so in its signature: `-> !Unpaid`. Cy still owes 120:

```rux
let owing = Stay { guest: "Cy", key: Key { room: 3 }, owed: 120 };
owing.CheckOut() catch {
    e => {
        PrintLine("    {} still to pay", e.owed);
    }
};
```

```text
check out owing:
    key 3 back at the desk
    120 still to pay
```

A failed ending ends the value too. The `throw` leaves the method, the key is destroyed on the way out, and only then does the error reach the `catch`. After the call `owing` is finished, whichever way it went:

```text
error: 'owing' is used after it was ended
  note: 'owing' was ended by 'CheckOut' at 87:10
```

The failure is reported, so it has to be handled, like that of any call that can fail — here with `catch`, as in [Catch](/docs/learn/catch).

## An ending that returns a field

Inside an ending method the fields are locals, so one of them can be given away. `HandOverKey` gives the key to the caller and ends the rest of the stay:

```rux
// Gives the key away to the caller, so only the rest of the stay ends here.
func HandOverKey(~self) -> Key {
    PrintLine("    {} hands key {} on", self.guest, self.key.room);
    return self.key;
}
```

```rux
let moving = Stay { guest: "Dee", key: Key { room: 4 }, owed: 0 };
let key = moving.HandOverKey();
PrintLine("    the new guest holds key {}", key.room);
```

The key lives on with its new owner, `key`, and goes back to the desk only at the end of `Main`. Anywhere else a field cannot be given away by itself — the rest of the value would be left without it, and the destructor needs the whole value. Inside an ending method it can, because the value is being taken apart anyway and no destructor will run.

## How a value can end

```mermaid
flowchart LR
    v(["a value with<br/>a destructor"])
    v -- "scope ends, `return`,<br/>`=` replaces it" --> d["destructor,<br/>then fields"]
    v -- "`destroy value;`" --> d2["destructor now,<br/>then fields"]
    v -- "`value.CheckOut()`<br/>a `~self` method" --> m["method body,<br/>then the fields left;<br/>no destructor"]
    v -- "given away" --> g["the new owner<br/>ends it later"]
```

|                     | Destructor           | `destroy value;`  | `~self` method       |
| ------------------- | -------------------- | ----------------- | -------------------- |
| Who starts it       | the compiler         | you, on that line | you, by calling it   |
| Runs the destructor | it is the destructor | yes               | no — it replaces it  |
| Can return a value  | no                   | no                | yes, such as a field |
| Can fail            | no                   | no                | yes, `-> !E`         |
| The name afterwards | out of scope         | finished          | finished             |

`~self` takes the destructor's place, so only a type that declares a destructor can have it. A type with nothing to replace is taken apart with a pattern instead, as [Replace and swap](/docs/learn/replace-swap) shows.

## The program

The whole lesson is one package in the [Examples repository](https://github.com/rux-lang/Examples/tree/main/Ownership/Destroy). Its comments explain every step.

<!-- sync:program:start -->

```rux [Src/Main.rux]
// Destructor showed when a value's life ends: at the end of its scope, at a return, or when `=`
// replaces it. Two things a destructor cannot do. It cannot run sooner than that, and it cannot
// report a problem, because no error may leave a destructor.
//
// `destroy value;` ends a value now. The destructor runs on the spot, then the value's fields, and
// the value is not destroyed again where its scope ends. The name is finished, as after giving the
// value away, so any later use is an error.
//
// A method whose receiver is `~self` ends the value instead of its destructor. The call takes the
// value, the destructor does not run, and inside the method every field of `self` is a local of
// its own: the method may give one away, and the fields it leaves are destroyed when it returns.
// Unlike a destructor, such a method can return a result, and it can fail.
//
// A hotel stay shows both. A stay holds a room key. When the hotel has to close a stay, its
// destructor does it. A guest who checks out ends the stay with `CheckOut`, which can refuse an
// unpaid bill, and a guest who passes the room on ends it with `HandOverKey`, which keeps the key.
import Io::PrintLine;

struct Key {
    room: int32;
}

extend Key {
    destructor {
        PrintLine("    key {} back at the desk", self.room);
    }
}

struct Unpaid {
    owed: int32;
}

struct Stay {
    guest: char8[..];
    key: Key;
    owed: int32;
}

extend Stay {
    // The end nobody chose: the hotel closes the stay.
    destructor {
        PrintLine("    the hotel closes {}'s stay", self.guest);
    }

    // Ends the stay in place of the destructor, and fails while the bill is open. Either way the
    // stay is over and the key, still a field, is destroyed when the method leaves.
    func CheckOut(~self) -> !Unpaid {
        if self.owed > 0 {
            throw Unpaid { owed: self.owed };
        }
        PrintLine("    {} checks out", self.guest);
    }

    // Gives the key away to the caller, so only the rest of the stay ends here.
    func HandOverKey(~self) -> Key {
        PrintLine("    {} hands key {} on", self.guest, self.key.room);
        return self.key;
    }
}

func Main() -> int {
    // `destroy` ends Ada's stay before the end of `Main`.
    PrintLine("destroy:");
    let early = Stay { guest: "Ada", key: Key { room: 1 }, owed: 0 };
    destroy early;
    PrintLine("    Ada's stay is over");

    // The name is finished from here on:
    //
    //     PrintLine("{}", early.guest);
    //
    // error: 'early' is used after it was destroyed
    //   note: 'early' was destroyed with 'destroy' at 65:5

    // A `~self` method ends the stay without the destructor. The key goes after the method's body.
    PrintLine("check out:");
    let paid = Stay { guest: "Bob", key: Key { room: 2 }, owed: 0 };
    paid.CheckOut() catch {
        e => {
            PrintLine("    {} still to pay", e.owed);
        }
    };

    // A failed ending ends the value too: the key is back before the error reaches the caller.
    PrintLine("check out owing:");
    let owing = Stay { guest: "Cy", key: Key { room: 3 }, owed: 120 };
    owing.CheckOut() catch {
        e => {
            PrintLine("    {} still to pay", e.owed);
        }
    };

    // After the call `owing` is finished, like a value given away:
    //
    //     PrintLine("{}", owing.guest);
    //
    // error: 'owing' is used after it was ended
    //   note: 'owing' was ended by 'CheckOut' at 87:10

    // A field given away by the method lives on with its new owner.
    PrintLine("hand over:");
    let moving = Stay { guest: "Dee", key: Key { room: 4 }, owed: 0 };
    let key = moving.HandOverKey();
    PrintLine("    the new guest holds key {}", key.room);

    // `~self` takes the destructor's place, so a type without one cannot have it. Write
    // `func Settle(~self)` in an `extend Unpaid` block and it is refused:
    //
    // error: '~self' replaces a destructor, and 'Unpaid' has none
    //   help: write 'self'

    PrintLine("end of Main:");
    return 0;
}
```

## Common mistakes

::mistake
**Using a name after `destroy`.**\
After `destroy early;`, `PrintLine("{}", early.guest)` fails with:

```text
error: 'early' is used after it was destroyed
```

The note points at the `destroy`. After an ending method the message reads "is used after it was ended" instead, and the note names the method. Either way, the value is gone — move the use above the line that ends it.
::

::mistake
**Destroying a part of a value.**\
`destroy paid.key;` fails with:

```text
error: 'key' is a part of 'paid' and cannot be destroyed by itself
  help: assign the part a new value, which destroys the old one
```

The stay would be left without a key, and its own end could not tell. Destroy the whole stay, or replace the key: `=` destroys the old value as it installs the new one.
::

::mistake
**Ignoring an ending that can fail.**\
`owing.CheckOut();` on its own fails with:

```text
error: 'CheckOut' can fail with 'Unpaid', and the result is not used
  help: pass the error on with '!', ignore it with '!!;', or handle it with 'catch { ... }'
```

The stay ends either way, but the unpaid bill would be lost without a word. Handle it with `catch`, as the program does, or write `owing.CheckOut() !!;` to drop it on purpose.
::

::mistake
**A `~self` method on a type without a destructor.**\
`func Settle(~self)` in an `extend Unpaid` block fails with:

```text
error: '~self' replaces a destructor, and 'Unpaid' has none
  help: write 'self'
```

There is nothing for the method to replace. Write a plain `self` receiver, as the help says.
::

## Try it yourself

1. Give Bob an open bill of 30. Which lines does "check out:" print now, and in what order?
2. Add `destroy key;` after the line that prints "the new guest holds key 4". Where does "key 4 back at the desk" move to?
3. Add an ending method `func Leave(~self)` to `Stay` that prints a line, then runs `destroy self.key;`, then prints another line. Call it on a new stay and watch where the key goes back to the desk.
