# Defer return

::note
<!-- sync:needs:start -->

**You'll need**: [Defer](/docs/learn/defer), [Mutating method](/docs/learn/mutating-method), [Destructor](/docs/learn/destructor)
<!-- sync:needs:end -->

::

`return` and [`defer`](/docs/learn/defer) meet at the end of a function, and the order between them is fixed. `return value;` works out its value first and **keeps** it; only then do the deferred statements run. Whatever they change afterwards, the caller still receives the kept value.

That sounds like a detail, but it makes a useful pattern possible: "hand out the current value, then move on" becomes a two-line function, with no temporary variable to hold the old value. And [destructors](/docs/learn/destructor) run at the same moment, in one sequence with the deferred statements.

## The order at the end of a function

`Countdown` registers two deferred statements and then returns its local:

```rux
func Countdown() -> int32 {
    var remaining: int32 = 3;
    defer PrintLine("    deferred code sees remaining = {}", remaining);
    defer remaining = 0;
    return remaining;
}
```

Step by step, as the function ends:

```mermaid
flowchart LR
    r["`return remaining`<br/>works out `3`<br/>and keeps it"] --> d1["`defer remaining = 0`<br/>(registered last, runs first)"]
    d1 --> d2["`defer PrintLine(…)`<br/>prints `remaining = 0`"]
    d2 --> c["the caller<br/>receives `3`"]
```

```
countdown:
    deferred code sees remaining = 0
    returned 3
```

Two things are worth noticing in that output.

The `PrintLine` shows 0, not 3. A deferred statement is evaluated **when it runs**, not when it is registered, so it reads `remaining` after the reset has happened. And the reset _did_ happen: the local really is 0. It simply makes no difference to the caller, who gets the 3 that `return` had already kept.

## Hand out, then advance

A ticket dispenser shows a number. Taking a ticket gives you that number, and the display moves on to the next:

```rux
struct Dispenser {
    next: int32;
}

extend Dispenser {
    // Returns the current ticket, then advances the dispenser.
    func Take(&var self) -> int32 {
        defer self.next += 1;
        return self.next;
    }
}
```

`return self.next` keeps the current number; the deferred `self.next += 1` then advances the dispenser. Without `defer`, the same method needs a temporary:

```rux
let ticket = self.next;
self.next += 1;
return ticket;
```

Both are correct. The `defer` version says what the method is for in its last line (return the current ticket) and puts the bookkeeping on the line before it.

```rux
var dispenser = Dispenser { next: 1 };
let first = dispenser.Take();
let second = dispenser.Take();
```

`first` is 1, `second` is 2, and the dispenser now shows 3. The method changes `self`, so its receiver is `&var self`, as in [Mutating method](/docs/learn/mutating-method).

| Statement               | When it is evaluated           | What the caller sees         |
| ----------------------- | ------------------------------ | ---------------------------- |
| `return self.next;`     | first: its value is kept       | the kept value               |
| `defer self.next += 1;` | after the return value is kept | the change, on its next call |

## Defers and destructors in one sequence

A `Chore` is a job that is done when its value ends; its destructor prints the job:

```rux
// A job that is done when its value ends.
struct Chore {
    name: char8[..];
}

extend Chore {
    destructor {
        PrintLine("    {}", self.name);
    }
}
```

`CloseShop` mixes chores and a deferred statement across two scopes, and returns from the inner one:

```rux
// The `return` leaves two scopes. `till` is in the inner one, so it goes first, then the deferred
// statement, then `sign`, which was declared before it.
func CloseShop(served: int32) -> int32 {
    let sign = Chore { name: "take the sign in" };
    defer PrintLine("    switch the lights off");
    if served > 0 {
        let till = Chore { name: "count the till" };
        PrintLine("    last customer served");
        return served;
    }
    return 0;
}
```

After `return served;` keeps its value, everything still pending runs as **one** sequence. The innermost scope goes first, and in each scope whatever was declared or registered last goes first. A deferred statement and a value with a destructor take their turns alike:

```mermaid
flowchart LR
    r["`return served`<br/>keeps `2`"] --> t["inner scope:<br/>`till` ends<br/>count the till"]
    t --> l["outer scope, last first:<br/>the `defer`<br/>switch the lights off"]
    l --> s["then `sign` ends<br/>take the sign in"]
    s --> c["the caller<br/>receives `2`"]
```

So a local declared _after_ a `defer` is destroyed before the deferred statement runs, and one declared _before_ it is destroyed after. That is what lets a deferred statement use any value declared above it: the value is still alive when the statement runs.

## The program

The whole lesson is one package in the [Examples repository](https://github.com/rux-lang/Examples/tree/main/Ownership/DeferReturn). Its comments explain every step.

<!-- sync:program:start -->

```rux [Src/Main.rux]
// `return` and `defer` meet at the end of a function, and the order between them is fixed:
// `return value;` works out its value first and keeps it, and only then do the deferred
// statements run. Whatever they change afterwards, the caller still receives the kept value.
//
// That makes "hand out the current value, then move on" a two-line function. A ticket dispenser
// returns the number it is showing and advances to the next one, without a temporary variable to
// hold the old number.
//
// Destructors run at the same moment. After the value is kept, the deferred statements and the
// destructors of the live locals run as one sequence: the innermost scope first, and in each
// scope the last declared first. So a local declared after a `defer` is destroyed before the
// deferred statement runs, and one declared before it is destroyed after it.
import Io::PrintLine;

// Both deferred statements run after the return value is kept. In reverse order, so the reset
// runs first and the `PrintLine` then shows that the local really changed. The caller gets 3.
func Countdown() -> int32 {
    var remaining: int32 = 3;
    defer PrintLine("    deferred code sees remaining = {}", remaining);
    defer remaining = 0;
    return remaining;
}

struct Dispenser {
    next: int32;
}

extend Dispenser {
    // Returns the current ticket, then advances the dispenser.
    func Take(&var self) -> int32 {
        defer self.next += 1;
        return self.next;
    }
}

// A job that is done when its value ends.
struct Chore {
    name: char8[..];
}

extend Chore {
    destructor {
        PrintLine("    {}", self.name);
    }
}

// The `return` leaves two scopes. `till` is in the inner one, so it goes first, then the deferred
// statement, then `sign`, which was declared before it.
func CloseShop(served: int32) -> int32 {
    let sign = Chore { name: "take the sign in" };
    defer PrintLine("    switch the lights off");
    if served > 0 {
        let till = Chore { name: "count the till" };
        PrintLine("    last customer served");
        return served;
    }
    return 0;
}

func Main() -> int {
    PrintLine("countdown:");
    let result = Countdown();
    PrintLine("    returned {}", result);

    PrintLine("tickets:");
    var dispenser = Dispenser { next: 1 };
    let first = dispenser.Take();
    let second = dispenser.Take();
    PrintLine("    took {} and {}, now showing {}", first, second, dispenser.next);

    PrintLine("closing:");
    let served = CloseShop(2);
    PrintLine("    returned {}", served);
    return 0;
}
```

## Common mistakes

::mistake
**Expecting a deferred change to reach the caller.**\
`defer remaining = 0;` does reset the local, but `Countdown()` still returns 3. The return value was kept before any deferred statement ran, and the deferred statement reads `remaining` when it runs, not when it is registered. If the caller must see the change, make it before the `return`.
::

::mistake
**Advancing through a read-only receiver.**\
With `func Take(&self)`, the deferred `self.next += 1;` fails with:

```text
error: cannot modify data through immutable reference '&Dispenser'
```

Deferred code is checked like any other code in the function: changing `self` needs `&var`.
::

::mistake
**Returning a value a defer still uses.**\
A function that builds a chore, defers `PrintLine("    hired for {}", chore.name);`, and then ends with `return chore;` fails with:

```text
error: 'chore' is given away here, and the deferred statement on line 62 still lends it
  help: give 'chore' away after the scope ends, or assign it a new value instead
```

The return value is kept before the deferred statement runs, so the chore would already belong to the caller when the deferred statement reads it. Print before the `return` instead.
::

## Try it yourself

1. Swap the two `defer` lines in `Countdown`. What does the deferred `PrintLine` show now, and does the returned value change?
2. Call `CloseShop(0)` instead of `CloseShop(2)`. Which lines print, and in what order?
3. In `CloseShop`, move `let sign = …` to the line after the `defer`. Predict the new order of the three closing lines, then run it.
4. Write `func Next(counter: &var int32) -> int32` that returns the counter's current value and then adds 1 to it, using `defer`. Call it twice on a `var` that starts at 5.
