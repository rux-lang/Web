# Copy and Move

Copying and moving are operations a type has or does not have, and the compiler generates both: a copy duplicates a value's bytes, and a move — what happens when a value is [given away](/docs/lang/ownership/overview) — is a byte copy followed by forgetting the source. Neither runs user code, and neither is written: a named value in a by-value position is copied when its type can be, and moved otherwise. What a type supports follows from what it holds, and two attributes take a capability away.

## Copyable and move-only types

A type is **copyable** when it is plain data: it declares no [destructor](/docs/lang/ownership/destructors), every field, element and payload it holds is copyable, and it is not `#NoCopy`.

| Copyable                                                                                  | Move-only                                               |
| ----------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| numbers, `bool`, characters, raw pointers                                                 | a type that declares a `destructor`                     |
| slices `T[..]` and `var T[..]`, function values                                           | a type holding a move-only field, element or payload    |
| structures, tuples, variants, unions, optionals, sums and arrays `T[N]` of copyable types | a `#NoCopy` or `#NoMove` type, and anything holding one |

`=` from a named copyable value copies its bytes. A type with a destructor owns resources, so copying its bytes would leave two owners to release them; it moves instead. Copyability is decided once per type, so a structure with a move-only field is move-only itself.

A named move-only local or parameter in any by-value position — a binding, argument, receiver, return, assignment, aggregate field, field shorthand or conditional arm — is given away, and a later use of the name is an error:

```text
error: 'text' is used after it was given away
  help: lend it with '&text' where it is only read, or clone it where both uses need a value
```

A fresh temporary — a call result, a literal, a constructor call — has no other owner and is given away too. Where a copy is wanted, it is asked for with `Clone()`; where the value is only read, it is lent with `&`.

## Clone

A move-only value is duplicated only by an ordinary method, by convention `Clone(&self) -> Self`, called where the copy is wanted. `Core::Ownership::Cloneable` is the interface that names it, so generic code duplicates a value under `T: Cloneable`:

```rux
struct Note {
    text: String;
}

extend Note {
    func Clone(&self) -> Self {
        return Note { text: self.text.Clone() };
    }
}

func Keep(note: &Note) -> Note {
    return note.Clone();    // a fresh value, given to the caller
}
```

For `String`, `Clone` allocates, and running out of memory panics as every allocation in a collection or a string does.

`=` never runs user code. A copy operator with a body, `func =(&var self, other: &T) { … }`, is rejected:

```text
error: custom copy hooks are not supported
  note: '=' copies the bytes of plain data and never runs user code
  help: implement 'func Clone(&self) -> Self' on 'T' and call it where a copy is needed
```

## Assignment

Assigning over a live value is a replacement. The new value is produced first, then the old value is [destroyed](/docs/lang/ownership/destructors) once, and then the new one is installed: `value = MakeValue();`, `value = other;` and `value = other.Clone();` each install a value nobody else holds. A field, a tuple element and an element of an array or a slice are destinations like any other — `holder.item = value` and `items[i] = value` destroy what the place held. A write through a raw pointer initializes the storage it addresses and destroys nothing. Giving a place to itself, `value = value;`, is `cannot give 'value' to itself`.

## Prohibiting copies

`#NoCopy` on a struct, variant or union makes it move-only even with no destructor. That suits plain data that must not be duplicated, such as a handle a destructor does not release:

```rux
#NoCopy
struct RoomKey {
    room: int32;
}

func CheckOut(key: RoomKey) {}

func Main() -> int {
    let key = RoomKey { room: 4 };
    CheckOut(key);                    // given away: 'key' is finished
    return 0;
}
```

Every by-value position gives the key away, and the name is finished after it:

| Where             | Written                | Afterwards             |
| ----------------- | ---------------------- | ---------------------- |
| A binding         | `let spare = key;`     | `spare` holds the key  |
| An argument       | `CheckOut(key)`        | the callee holds it    |
| A return          | `return key;`          | the caller holds it    |
| A field value     | `Booking { key: key }` | the booking holds it   |
| A field shorthand | `Booking { key }`      | the same as `key: key` |
| A read-only loan  | `Look(&key)`           | `key` still holds it   |

A `#NoCopy` value lent to a reference parameter is written with `&`, as any move-only value is: see [When the loan must be written](/docs/lang/references/overview#when-the-loan-must-be-written).

## Prohibiting moves

`#NoMove` prohibits moving as well, so it implies `#NoCopy`. A value of such a type stays in the storage it was created in, which suits a value that points into itself; it is shared through a pointer or a reference. Giving one away is an error:

```text
error: moving type 'ListNode' is prohibited
  note: a '#NoMove' type, or one holding a '#NoMove' value, stays where it was built
  help: borrow the value or construct a distinct replacement instead
```

Such a value is still created in place from a temporary, because nothing can have taken a temporary's address, and [`destroy`](/docs/lang/ownership/ending#destroy) ends it where it lies:

```rux
#NoMove
struct ListNode {
    next: *var ListNode;
}

func IsLast(node: &ListNode) -> bool {
    return node.next == null;
}

func Main() -> int {
    let node = ListNode { next: null };    // built where it lives
    PrintLine("{}", IsLast(&node));
    return 0;
}
```

Both attributes take no arguments, are written without parentheses, and may each be written once per declaration. They prohibit the capability everywhere, regardless of visibility.

A move operator with a body is rejected with `custom move hooks are not supported` and `help: a type that must stay in place uses '#NoMove'`: a move never runs user code. The older bodyless declarations prohibit nothing:

```text
error: a bodyless 'func =' does not prohibit copying
  help: mark 'T' with '#NoCopy' instead
```

A bodyless `func <-` is rejected the same way, `a bodyless 'func <-' does not prohibit moving`, in favour of `#NoMove`. A bodyless function in an [interface](/docs/lang/interfaces/overview) is still an ordinary requirement.

## Generic code

A value of a type parameter counts as move-only inside generic code, so a local or a parameter of type `T` written bare is given away, and a second use of it is an error whatever `T` turns out to be. Under `T: Copyable` it is copied instead, and `Clone` under `T: Cloneable` makes an explicit copy. A field or an element of type `T` read by value is still a copy, checked for each instantiation, and instantiating it with a move-only type reports the copy in the generic body:

```text
error: cannot copy 'Owner', which owns resources
  note: the generic code copies a 'T' here, which is 'Owner' in this instantiation
  help: bound the type parameter by 'Copyable'
```

A `T: Copyable` bound moves the check to the call, which is refused for a move-only type argument: `type argument 'Owner' does not satisfy interface bound 'Copyable' on type parameter 'T'`. See [Bounds](/docs/lang/generics/bounds).

## Partial moves

A field, a tuple element or an array element cannot be given away on its own. A value that is partly there would leave nothing able to say what to destroy when its owner's scope ends, so a value is given away whole or not at all. With a local `var parcel`, `let gift = parcel.gift;` is refused:

```text
error: 'gift' is a field of 'parcel' and cannot be given away by itself
  note: only a local, a parameter or a temporary is given away; the rest of the value would be left without it
  help: take it with 'Replace(&var parcel.gift, value)' or 'Swap', or take 'parcel' apart with a pattern
```

The help names the two ways out. [`Replace`](/docs/api/core/ownership#replace) and [`Swap`](/docs/api/core/ownership#swap), from `Core::Ownership`, take the part and leave a value in its place. They write the place, so for a `let` local or a by-value parameter the help offers only the pattern: `take 'parcel' apart with a pattern; it cannot be taken with 'Replace' or 'Swap', which write the place`. A moving [destructuring pattern](/docs/lang/bindings/destructuring) takes the **whole** value apart, so that every part gets exactly one new owner:

```rux
struct Item {
    name: char8[..];
}

extend Item {
    destructor {
        PrintLine("{} destroyed", self.name);
    }
}

struct Parcel {
    wrapping: Item;
    gift: Item;
}

func Unwrap(parcel: Parcel) -> Item {
    let Parcel { wrapping: _, gift } = parcel;    // the wrapping is destroyed here
    return gift;
}
```

- A part bound to a name belongs to that binding and is destroyed with it.
- A part bound to `_`, or a structure field the pattern leaves out, has no owner left, so it is destroyed on the spot — at the `let`, or at the top of a `match` arm — in the order the parts appear in the pattern.

A destructuring `let` owns what it takes apart, so a named owning value written after `=` is given to it. Tuples may always be split this way. A structure may be split only when it declares no destructor of its own, because a destructor runs on the whole value:

```text
error: cannot split 'Sealed' with a moving pattern, because it declares a destructor
  note: the destructor runs on the whole value, so no part of it can be taken out on its own
  help: bind the whole value and read its fields, or match a value that stays with its owner
```

A structure with a destructor hands its fields on through a method that [ends it](/docs/lang/ownership/ending#ending-methods), `func Into(~self)`, instead.

| You want                      | Write                                              | Allowed when                    |
| ----------------------------- | -------------------------------------------------- | ------------------------------- |
| one field, leaving a value    | `Replace(&var parcel.gift, Item { name: "card" })` | `parcel` may be written         |
| every part, each to one owner | `let Parcel { wrapping: _, gift } = parcel;`       | the structure has no destructor |
| a field, ending the value     | a method taking `~self` that returns `self.gift`   | the structure has a destructor  |
| to read a field               | `parcel.gift.name`                                 | always — reading copies data    |

## Matching and ownership

A `match` that binds parts of its subject takes them, the same way a destructuring `let` does. `match value { … }` on a named owning value takes the subject; a temporary subject, such as a `Clone` result, is taken directly. A match on a named plain-data value matches a **copy** of it, which its arms own; the original stays with its owner. `match &value { … }` lends the subject instead, so its arms bind references and nothing can be given away from them. A named owning subject is kept with `match &value`, or matched as a clone with `match value.Clone()`.
