# Defer

A `defer` statement registers a statement now and runs it when the enclosing scope ends, by whichever way it ends. Cleanup written once, on the line after the work it undoes, then covers every exit — including ones added later.

## Syntax

```text
defer statement
```

The deferred part is exactly one statement: an expression statement such as a call, an assignment, a statement with its own body such as `if`, or a plain block `{ … }`, which defers every statement in it:

```rux
struct Valve {
    name: char8[..];
}

extend Valve {
    func Open(&self) {
        PrintLine("open {}", self.name);
    }

    func Close(&self) {
        PrintLine("close {}", self.name);
    }
}

func Fill(litres: int32) -> bool {
    let supply = Valve { name: "supply" };
    supply.Open();
    defer supply.Close();

    let drain = Valve { name: "drain" };
    drain.Open();
    defer {
        drain.Close();
        PrintLine("drained");
    }

    if litres > 100 {
        return false;
    }
    PrintLine("filling {} litres", litres);
    return true;
}
```

Both exits close both valves, the drain first.

## Semantics

**Registration happens at run time.** A `defer` counts only once execution reaches it. A `return` before the `defer` line leaves without running it, and a `defer` inside a branch that is not taken never registers.

**It belongs to its scope.** A deferred statement runs when the block it is written in ends: the function body, the body of an `if`, a plain block, or one pass of a loop body — so a `defer` in a loop runs once per pass, not once after the loop. The scope may end by reaching its closing brace, by `return`, by `break` or `continue`, by `?` propagating an absence, or by an error leaving it for its handler or out of the function through its error side; a `break` or `continue` runs the defers of the pass and of every inner scope it leaves.

**Last registered, first run.** Several defers in one scope run in reverse registration order, and the defers of nested scopes run innermost first.

**It is evaluated when it runs.** A deferred statement reads its variables at the end of the scope, not at the `defer` line, so it sees every change made in between: after `var n = 1; defer Print(n); n = 2;` the deferred call prints `2`.

**Each function has its own.** A function's defers run when that function's scopes end; calling a function never runs, or inherits, the caller's defers. Each instantiation of a generic function has its own as well.

## Return and defer

`return expr;` evaluates `expr` exactly once and keeps the result — copying it or giving it away into the return value — **before** any deferred statement runs. Whatever the defers change afterwards, the caller receives the kept value:

```rux
func Countdown() -> int32 {
    var remaining: int32 = 3;
    defer PrintLine("deferred code sees {}", remaining);
    defer remaining = 0;
    return remaining;
}
```

`Countdown()` returns `3`, and the deferred `PrintLine` prints `deferred code sees 0`. The same holds for every part of an aggregate return value. A `return` with no value runs the same defers without capturing anything, and an error that leaves the function through its error side runs them exactly as a return does, after the error has been captured.

That ordering makes "hand out the current value, then advance" a two-line method:

```rux
struct Dispenser {
    next: int32;
}

extend Dispenser {
    func Take(&var self) -> int32 {
        defer self.next += 1;
        return self.next;
    }
}
```

## Defers and destructors

When a scope ends, its deferred statements and the [destructors](/docs/lang/ownership/destructors) of its values run as **one sequence**, last declared first: a value declared after a `defer` is destroyed before the deferred statement runs, and one declared before it is destroyed after. Scopes are left innermost first, and a function's parameters go last.

```rux
func Party() {
    let ada = Guest { name: "Ada" };
    defer PrintLine("lights off");
    let bob = Guest { name: "Bob" };
    defer PrintLine("music off");
}
```

```mermaid
flowchart LR
    r["return value<br/>captured"] --> s["defers and destructors<br/>last declared first"]
    s --> p["parameters<br/>destroyed"]
    p --> c["control reaches<br/>the caller"]
```

`Party` prints `music off`, `Bob leaves`, `lights off`, `Ada leaves`: each deferred statement runs while everything declared before it is still there. On a `return`, the full order is: the return value is captured, then the defers and the locals' destructors run in that one sequence, then the parameters are destroyed.

|            | Destructor                 | `defer`                        |
| ---------- | -------------------------- | ------------------------------ |
| Belongs to | a type — every value of it | one piece of work in one scope |
| Written    | once, in `extend T`        | where the work starts          |
| Runs       | when a value's life ends   | when the enclosing scope ends  |

A destructor cleans up after a value. `defer` is for cleanup that belongs to a piece of work rather than to any one value's life; `rux lint` reports a `defer` that only releases a local, `'defer buffer.Release()' releases what a destructor should`, because its type wants a destructor.

## Defers and loans

Because a value declared before a `defer` outlives the deferred statement, the statement may **lend** it, and its loan starts when it runs, not where it is written:

```rux
func Greet(guest: &Guest) {
    PrintLine("bye {}", guest.name);
}

func Visit() {
    let cy = Guest { name: "Cy" };
    defer Greet(&cy);
}
```

`Visit` prints `bye Cy`, then `Cy leaves`. A deferred statement cannot **give** a value away, since the value still belongs to the scope that is ending:

```text
error: a deferred statement cannot give 'cy' away
  note: it runs where its scope ends, and a value given away then is still owned by that scope
  help: lend it with '&cy'
```

From the `defer` to the end of its scope, a value it lends is not given away — `return` and `throw` included — nor [destroyed](/docs/lang/ownership/ending#destroy). It may be assigned, and the deferred statement then sees the new value:

```text
error: 'cy' is given away here, and the deferred statement on line 7 still lends it
  note: a deferred statement runs where its scope ends, after the value being returned or given away is gone
  help: give 'cy' away after the scope ends, or assign it a new value instead
```

## Panics

A [panic](/docs/lang/errors/panics) does not unwind, so no deferred statement runs — not in the panicking function and not in its callers.

## Leaving from a defer

A deferred statement runs while its scope is already being left, so it cannot leave it another way. `return`, `throw` and `?` inside a `defer` are refused, and so are a `break` or `continue` that would leave it; one that leaves a loop written inside the deferred statement is fine:

```text
error: 'return' cannot leave a deferred statement
error: '?' cannot leave a deferred statement
error: 'break' cannot leave a deferred statement
```

No error may leave it either, so a call in it that can fail is handled there, with `!!` or `catch`. Passing the error on with `!` is refused:

```rux
defer Close(&file) !!;
```

```text
error: an error cannot leave a deferred statement
  note: a deferred statement runs while its scope is already being left
  help: handle it with '!!' or 'catch { ... }'
```

The same holds in a [destructor](/docs/lang/ownership/destructors), as `an error cannot leave a destructor`.

## No `finally`

There is no `finally`: it is reserved and refused with `'finally' is not supported` and `help: use 'defer'`. Cleanup that must run on every exit is a `defer` or a destructor. When an error leaves a scope, the defers registered in it run and its locals are destroyed before the error reaches its handler:

```rux
func Process(path: char8[..]) -> !FileError {
    let file = Open(path)!;
    defer Release(&file);
    Write(&file)!;    // an error here runs Release, then reaches the caller
}
```

See [Handling errors](/docs/lang/errors/handling).
