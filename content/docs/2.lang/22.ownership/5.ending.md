# Ending a value

A value's life normally ends where its owner lets go of it — at the end of a scope, at a replacement, or where the paths of a branch rejoin — and its [destructor](/docs/lang/ownership/destructors) runs there. Two forms end a value on purpose instead. The statement **`destroy place;`** runs the usual destruction now, before the scope would. A method that takes its receiver as **`~self`** ends the value in place of the destructor, so the ending can return what it keeps, and can fail.

```text
destroy-stmt  = "destroy" place ";"
ending-method = "func" identifier "(" "~self" { "," parameter } ")" [ "->" type ] block
```

```rux
struct Handle {
    id: int32;
}

extend Handle {
    destructor {
        PrintLine("handle {} released", self.id);
    }
}

struct Unsaved {
    lines: int32;
}

struct Journal {
    name: char8[..];
    handle: Handle;
    pending: int32;
}

extend Journal {
    destructor {
        PrintLine("{} dropped with {} lines unsaved", self.name, self.pending);
    }

    // Ends the journal in place of the destructor, and fails while lines are unsaved.
    func Close(~self) -> !Unsaved {
        if self.pending > 0 {
            throw Unsaved { lines: self.pending };
        }
        PrintLine("{} closed", self.name);
    }

    // Ends the journal and gives its handle to the caller.
    func IntoHandle(~self) -> Handle {
        return self.handle;
    }
}

func Open(name: char8[..], id: int32, pending: int32) -> Journal {
    return Journal { name, handle: Handle { id }, pending };
}

func Main() -> int {
    let draft = Open("draft", 1, 2);
    destroy draft;
    PrintLine("after destroy");

    let saved = Open("saved", 2, 0);
    saved.Close() catch {
        e => PrintLine("{} lines unsaved", e.lines),
    };

    let busy = Open("busy", 3, 5);
    busy.Close() catch {
        e => PrintLine("{} lines unsaved", e.lines),
    };

    let moved = Open("moved", 4, 0);
    let handle = moved.IntoHandle();
    PrintLine("kept handle {}", handle.id);
    return 0;
}
```

```text
draft dropped with 2 lines unsaved
handle 1 released
after destroy
saved closed
handle 2 released
handle 3 released
5 lines unsaved
kept handle 4
handle 4 released
```

## `destroy`

`destroy place;` destroys a value where it lies: its destructor, if its type declares one, then its parts, last declared first, and nothing at all for plain data. On a local or a parameter it **ends** the value: the value is not destroyed again where its scope ends, and the name is finished, as after giving the value away:

```text
error: 'draft' is used after it was destroyed
  note: 'draft' was destroyed with 'destroy' at …
```

Nothing is moved, so a [`#NoMove`](/docs/lang/ownership/copy-and-move#prohibiting-moves) value, which cannot be given to a function that lets it go, ends the same way.

Through a [raw pointer](/docs/lang/pointers/overview), `destroy *p;` and `destroy p[i];` destroy what is there and leave the slot empty, so a later write through the pointer fills it and destroys nothing. This is how a container ends the elements its allocation holds:

```rux
let slots = Alloc(2 * sizeof(Handle)) as *var Handle;
// Safety: slots has room for two Handle values, filled here and ended below.
{
    slots[0] = Handle { id: 1 };
    slots[1] = Handle { id: 2 };
}
// Safety: both slots hold values, and nothing reads them afterwards.
{
    destroy slots[1];
    destroy *slots;
}
```

`destroy` ends a whole value that has a name, and nothing else:

| Written                                 | Error                                                           |
| --------------------------------------- | --------------------------------------------------------------- |
| `destroy pair.first;` on a local `pair` | `'first' is a part of 'pair' and cannot be destroyed by itself` |
| `destroy value;` with `value: &Tracked` | `a value reached through a loan cannot be destroyed`            |
| `destroy Make();`                       | `'destroy' ends a value that has a name`                        |
| `let z = destroy value;`                | `'destroy' is a statement and has no value`                     |
| `value.~();`                            | `'.~()' is not supported`, with `help: write 'destroy value;'`  |

A part of a live value is replaced instead, which destroys the old part: the help says `assign the part a new value, which destroys the old one`. A temporary is destroyed at the end of its statement already. A [deferred statement](/docs/lang/ownership/defer#defers-and-loans) that lends a value keeps it from being destroyed until the scope ends.

## Ending methods

A method may take its receiver as `~self`. The receiver is taken by value, as with `self`, so the caller's value is gone after the call, and the method **ends** it in place of the destructor: the destructor does not run.

Inside the method each field of `self` is a local of its own. It is read, written, lent, given away — `return self.handle;` above — or ended with `destroy self.handle;`, and a use after that is reported as for any local. The fields still there where the method exits, by `return`, `throw` or `!`, are destroyed, last declared first. That is why `busy.Close()` releases handle 3 before its error reaches the `catch` arm: a failed ending has ended the value too.

`self` itself is lent whole, to call another method, only while every field is still there, and it is never given away whole:

```text
error: 'self' is used whole after its field 'handle' was given away
  help: use the fields that are still there one by one
error: the receiver of a '~self' method is never given away whole
  help: give its fields away one by one
```

The caller's value is finished after the call, as after giving it away:

```text
error: 'busy' is used after it was ended
  note: 'busy' was ended by 'Close' at …
```

An ending can do what a destructor cannot. It can return a value, such as a field it hands on, and it can fail and say so in its signature, `-> !Unsaved`, because its caller handles the error where the call is written. A destructor runs where no call is written, so [no error may leave it](/docs/lang/ownership/destructors#syntax).

### Rules

- `~self` is accepted only on a structure that declares a destructor, because it takes the destructor's place: `func Reset(~self)` on a `Point` with none is `'~self' replaces a destructor, and 'Point' has none`, with `help: write 'self'`. A structure without one is taken apart with a [pattern](/docs/lang/ownership/copy-and-move#partial-moves) instead, as `let Parcel { gift, wrapping: _ } = self;`.
- The method is called on a value the caller owns. A field of a live value is not ended by itself — `journal.file.Close()` is `'file' is a field of 'journal' and cannot be ended by itself` — and a value behind a reference cannot be ended either: `cannot pass value behind reference '&var Handle' to by-value receiver of 'Close'`.
- A consuming conversion hands its storage on the same way, with nothing reset for a destructor to find: [`Vector::IntoIterator(~self)`](/docs/api/collections/vector#into-iterator) is the method a `for` loop calls when it takes a vector.
- Anywhere but the receiver position, `~self` is the bitwise complement of `self`.

## Choosing how a value ends

| The value should end                              | Write                            |
| ------------------------------------------------- | -------------------------------- |
| where its scope ends, its destructor running      | nothing                          |
| now, its destructor running                       | `destroy value;`                 |
| now, with a result or an error the caller handles | a method taking `~self`          |
| with a new value in its place                     | `value = replacement;`           |
| somewhere else                                    | give it away: `Keep(value)`      |
| in place, through a raw pointer                   | `destroy *p;` or `destroy p[i];` |
