# The Main function

An executable package starts at a function named `Main`, declared at the top level of the package — outside every `module` block. It has exactly one signature:

```rux
import Io::PrintLine;

func Main() -> int {
    PrintLine("Hello, Rux!");
    return 0;
}
```

When `Main` returns, the program ends, and the `int` it returns becomes the process's _exit status_: 0 for success, anything else for failure. A new executable package keeps `Main` in `Src/Main.rux`, but any file of the package may hold it. Library packages have no `Main`, and `rux run` refuses to run one.

## The signature

`Main` takes no parameters, has no type parameters, returns exactly `int` and cannot fail. Any other signature is an error that names what is wrong, with a note that explains why the result matters:

```rux
func Main() -> int32 {
    return 0;
}
```

```
error: 'Main' must be 'func Main() -> int', but it returns 'int32'
  note: the result of 'Main' is the process's exit status
  help: declare it as 'func Main() -> int' and return the exit status
```

| Declared                          | The error ends with                 |
| --------------------------------- | ----------------------------------- |
| `func Main()`                     | `but it has no result`              |
| `func Main() -> int32`            | `but it returns 'int32'`            |
| `func Main() -> float64`          | `but it returns 'float64'`          |
| `func Main(count: int) -> int`    | `but it takes parameters`           |
| `func Main<T>() -> int`           | `but it is generic`                 |
| `func Main() -> int ! StartError` | `but it returns 'int ! StartError'` |
| `func Main() -> !StartError`      | `but it returns '!StartError'`      |

## Steps that can fail

`Main` cannot fail, so the steps of a program that can fail go in a function of their own, and `Main` handles its error. The usual shape is a helper — by convention `Run` — whose steps pass their errors on with [`!`](/docs/lang/errors/propagation), and a `Main` that turns a failure into an exit status with [`!!`](/docs/lang/errors/fallible-values):

```rux
import Io::PrintLine;

variant StartError {
    MissingConfig
}

func Load(present: bool) -> int ! StartError {
    if !present {
        throw StartError::MissingConfig;
    }
    return 3;
}

func Run() -> !StartError {
    let count = Load(false)!;   // fails: Run passes the error on
    PrintLine("loaded {}", count);
}

func Main() -> int {
    Run() !! return 1;          // the program ends with status 1
    return 0;
}
```

`Run() !! return 1;` leaves `Main` with status 1 when `Run` fails and continues otherwise. When the helper itself computes the status, `return Run() !! 1;` does both in one line. Either way `Run`'s cleanup — its deferred statements and destructors — has already run by the time `Main` sees the error.

**Nothing prints the error for you.** A program that wants the user to see why it stopped handles the error with [`catch`](/docs/lang/errors/handling) and says so, choosing a status for each error:

```rux
import Io::PrintLine;

func Main() -> int {
    return Run() catch {
        .MissingConfig => {
            PrintLine("cannot start: no configuration");
            2
        }
    };
}
```

Here `Run` is declared `-> int ! StartError` and returns the status it wants on success. A [panic](/docs/lang/errors/panics) is different from an error: it stops the program at once, without cleanup.

## DllMain

A shared library built for Windows (`Type = "SharedLibrary"`) may declare a top-level function named `DllMain`. The Windows loader calls it when a process loads or unloads the library, and the library loads only if it returns a non-zero value. Its signature is the one Windows expects:

```rux
func DllMain(instance: *opaque, reason: uint32, reserved: *opaque) -> int32 {
    return 1;
}
```

Without a `DllMain`, the library loads as if one had returned 1. On other systems the name has no special meaning.
