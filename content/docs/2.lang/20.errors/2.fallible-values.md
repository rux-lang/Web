# Fallible Values

A _fallible_ `T ! E` holds either a success of type `T` or an error of type `E`. Every call to a function that [can fail](/docs/lang/errors/overview) evaluates to one: `Parse(text)`, with `Parse` declared `-> int ! ParseError`, is an `int ! ParseError`. Most calls take it apart on the spot (`Parse(text)!`, `Parse(text) !! 0`, `Parse(text) catch { … }`) and never store it. This page is about the others: an outcome kept as a value, decided later, or handed elsewhere.

```text
fallible-type = type "!" type
```

The examples on this page share one function:

```rux
variant ParseError {
    Empty,
    Invalid(int)
}

func Parse(text: char8[..]) -> int ! ParseError {
    if text.length == 0 {
        throw .Empty;
    }
    var value = 0;
    for i in 0..text.length {
        let c = text[i];
        if c < c8'0' || c > c8'9' {
            throw .Invalid(i as int);
        }
        value = value * 10 + ((c - c8'0') as int);
    }
    return value;
}
```

## Keeping an outcome

A call that is not taken apart is a value like any other. It can be bound, stored in a field, passed and returned wherever the same fallible type is expected:

```rux
struct Setting {
    name: char8[..];
    port: int ! ParseError;
}

let kept = Parse("8080");                               // int ! ParseError
let setting = Setting { name: "port", port: Parse("") };
```

A success converts to a fallible, as a value converts to an optional, so a known-good value needs no call:

```rux
let ready: int ! ParseError = 443;
```

An error enters a fallible only through [`throw`](/docs/lang/errors/overview#throwing), in the function that produced it. There is no case to build one with: `let k: int ! E = .Success(1);` is `error: case '.Success' needs an enum or variant, but the expected type is 'int ! E'`.

A kept fallible is taken apart later with the same forms as a call (`kept!`, `kept !! 0`, `kept catch { … }`) or with `is`, `if let` and `match`, below.

## Testing with is

`kept is E` asks whether the fallible holds an error of type `E`, and `kept is T` whether it holds a success. The test reads the fallible without consuming it, so it stays usable:

```rux
func Retry(first: int ! ParseError, text: char8[..]) -> int ! ParseError {
    if first is ParseError {
        return Parse(text);
    }
    return first;
}
```

| Test                       | `true` when the fallible holds                   |
| -------------------------- | ------------------------------------------------ |
| `kept is int`              | a success                                        |
| `kept is ParseError`       | an error                                         |
| `kept is IoError`          | an error of that member, when the error is a sum |
| `kept is .Failure(.Empty)` | an error matching the pattern after `.Failure`   |
| `kept is .Success(_)`      | a success, whatever its type                     |

A type on neither side is refused (`type 'bool8' is neither the success nor an error of 'int ! ParseError'`), and a fallible type after `is` is grouped, as in `value is (int ! ParseError)`. Like every `is`, the test binds nothing; [`if let`](/docs/lang/statements/if) takes a side out:

```rux
if let port: int = kept {
    PrintLine("port {}", port);
}
if let error: ParseError = Parse("") {
    PrintLine("refused");
}
```

## Matching by side

A [`match`](/docs/lang/patterns/match) takes a fallible apart. A typed pattern selects the side its type is on — or, for an error sum, one member or a subset of the members:

```rux
func Describe(outcome: int ! ParseError) -> char8[..] {
    return match outcome {
        port: int => if port < 1024 { "a privileged port" } else { "a port" },
        _: ParseError => "not a port"
    };
}
```

The arms must cover both sides; a missing one is named as the typed pattern that would take it:

```text
error: match on 'int ! ParseError' is not exhaustive; missing _: ParseError
```

`.Success(p)` and `.Failure(p)` name the two sides whatever their types. They are needed where a type cannot tell the sides apart (an `int ! int`, or generic code over `T ! E`):

```rux
func Succeeded<T, E>(outcome: &(T ! E)) -> bool {
    return match outcome {
        .Success(_) => true,
        .Failure(_) => false
    };
}
```

```text
error: cannot match 'int ! int' by type, because both sides are 'int'
  help: handle the error with 'catch { ... }', which sees only the error side
```

Neither spelling is a case of anything: they are patterns over a fallible, and nowhere else do they build or match a fallible.

## An unused fallible is an error

A fallible written as a statement on its own is refused, because the error in it would vanish unseen:

```text
error: 'Parse' can fail with 'ParseError', and the result is not used
  help: pass the error on with '!', ignore it with '!!;', or handle it with 'catch { ... }'
```

Binding it to `_` keeps nothing either, so `let _ = Parse(text);` is refused the same way, as `'Parse' can fail with 'ParseError', and '_' discards the result`. A fallible bound to a name is kept, and is destroyed at the end of its scope like any value. To drop an outcome on purpose, write `Parse(text) !!;`; see [Discarding an outcome](/docs/lang/errors/handling#ignoring-an-error).

## Nested fallibles

A fallible can itself be the success of another, written grouped: `(int ! ParseError) ! IoError` is a value that failed with an `IoError`, or succeeded with an `int ! ParseError`. It arises naturally when a function returns an outcome it has not decided:

```rux
func Read(ok: bool) -> char8[..] ! IoError {
    if !ok {
        throw IoError { code: 5 };
    }
    return "8080";
}

// Only IoError leaves through Load's own error side; the parse outcome is its success.
func Load(ok: bool) -> (int ! ParseError) ! IoError {
    let text = Read(ok)!;
    return Parse(text);
}
```

Each form handles one level, the outer one. `Load(true)!` passes an `IoError` on and continues with the `int ! ParseError`; `Load(true) !! Parse("0")` replaces an `IoError` with another parse outcome; and the inner level is handled after that, as in `(Load(true) !! Parse("0")) !! -1`. A `match` on the outer level selects `inner: int ! ParseError` or `e: IoError`.

## Ownership

A fallible owns its active side. A kept fallible whose success or error owns resources is given away when it is passed or assigned, and a later use is `'made' is used after it was given away`; one of plain data is copied. `is` borrows its operand, and `match &kept` lends it to the arms, which then cannot give a binding away. A `match` on the name itself takes the fallible, as it takes any owning subject, and an arm that binds nothing destroys what it holds.
