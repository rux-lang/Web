# Passing Errors On

Often the function that receives an error is not the one that should decide what it means. A postfix `!` after a call that can fail passes the error on: on success the expression continues with the success value; on failure the error leaves the enclosing function, through its own error side, at once.

```text
pass-on-expr = postfix-expr "!"
```

## Passing an error on

```rux
func ParseNumber(text: char8[..]) -> int ! DigitError {
    var value = 0;
    for i in 0..text.length {
        let c = text[i];
        if c < c8'0' || c > c8'9' {
            throw DigitError { position: i };
        }
        value = value * 10 + ((c - c8'0') as int);
    }
    return value;
}

func Area(width: char8[..], height: char8[..]) -> int ! DigitError {
    return ParseNumber(width)! * ParseNumber(height)!;
}
```

```mermaid
flowchart LR
    step["`ParseNumber(width)!`"] --> q{"Did it fail?"}
    q -- "no" --> go["the expression is the success;<br/>`Area` carries on"]
    q -- "yes" --> out["`Area` fails<br/>with the same error"]
```

`!` follows the operand it passes on, tight against it, and binds as a postfix operator — so it marks exactly one call, and a reader sees every place an error can leave:

| Write                                 | Passes on                                                         |
| ------------------------------------- | ----------------------------------------------------------------- |
| `ParseNumber(w)! * ParseNumber(h)!`   | each call's error, in turn                                        |
| `Counter::New(4)!.Doubled()!`         | the constructor's, then the method's                              |
| `let options = Parse(ReadText(p)!)!;` | the inner call's, then the outer one's                            |
| `kept!`                               | the error of a [kept fallible](/docs/lang/errors/fallible-values) |

- Evaluation runs from left to right and stops at the first `!` that finds an error: nothing to its right runs. In `Area`, a bad `width` means the second `ParseNumber` is never called.
- Leaving through `!` is an ordinary return: the error is captured first, then [deferred statements](/docs/lang/ownership/defer) run in reverse order and live locals are [destroyed](/docs/lang/ownership/destructors) — including the completed fields of an aggregate whose construction the error interrupted, and the arguments a call already holds when a later argument fails.
- A success continues as a plain value, so a chain carries on from it: `Counter::New(4)!.Doubled()!` calls `Doubled` on the new counter.
- An `x!` inside the operand of `!!` or `catch`, or in one of their arms, still leaves the function: each form handles only its own operand.

`!` needs an operand that can fail. On a plain value it is `'!' passes an error on, and 'int' has none`, and on an optional the help points at `?`:

```text
error: '!' passes an error on, and 'int?' has none
  help: write '?' to leave with 'none'
```

## The function must be able to fail

The error leaves through the enclosing function's own error side, so that function must declare one. In a function that cannot fail, `!` is refused:

```text
error: call to 'ParseNumber' can fail with 'DigitError', but 'Main' cannot fail
  help: handle the error here, as in '!! return 1', or move the steps that can fail into a function and handle its error in 'Main', as in 'return Run() !! 1;'
```

Handle the error there with [`!!` or `catch`](/docs/lang/errors/handling) instead. The success types need not match — only the error is passed on. A function returning an optional has no error side either: absence and failure are different things. [`Main`](/docs/lang/functions/main) can never fail, so the steps of a program that can fail go in a function whose error `Main` handles — see [Main cannot fail](/docs/lang/errors/overview#main-cannot-fail).

## The error must fit

An error is never converted on its way out. An error of type `E` leaves a function that fails with `F` only when:

| `E` and `F`                               | Example                                                               |
| ----------------------------------------- | --------------------------------------------------------------------- |
| the same type                             | `DigitError` into `DigitError`                                        |
| `E` is a member of the sum `F`            | `DigitError` into `DigitError \| RangeError`                          |
| `E` is a sum whose members are all in `F` | `DigitError \| RangeError` into `DigitError \| IoError \| RangeError` |

```rux
func ParsePercent(text: char8[..]) -> int ! DigitError | RangeError {
    let value = ParseNumber(text)!;
    if value > 100 {
        throw RangeError { value };
    }
    return value;
}
```

Any other pair is rejected:

```text
error: call to 'ParseNumber' can fail with 'DigitError', but 'ParseWidth' fails with 'SettingError'
  note: an error passes on only as itself, as a member of a sum, or as part of a larger sum; it is never converted
  help: handle the error with 'catch { ... }', or add 'DigitError' to the error of 'ParseWidth'
```

## Mapping errors

Adding context to an error, or converting it to the function's own error type, is a [`catch`](/docs/lang/errors/handling) arm that throws the mapped value. On success the arm never runs and the success continues unchanged. On failure `e` owns the complete error, the arm runs once, and its `throw` leaves the function:

```rux
func ParseWidth(text: char8[..]) -> int ! SettingError {
    let width = ParseNumber(text) catch { e => throw SettingError { name: "width", column: e.position + 1 } };
    return width;
}
```

The arm is the place to add what the error does not carry — here, the name of the setting and a 1-based column — and it may use any local in scope.

- The arm's own `throw` is not mapped again: an arm is outside its handler, so the error goes straight to the caller.
- The thrown value converts to the function's error type as any `throw` does; `throw 5` there, in a function that fails with `SettingError`, is a type error.
- An arm may leave another way — with `return`, or a call to `Panic` — or produce a fallback value instead of throwing.
- The arm reads and gives away the surrounding locals under the ordinary rules, on a path that always leaves; a local given away only inside it is still owned on the continuing path.

An error sum whose members map differently is matched, inside the arm or in a helper function:

```rux
func ToConfig(error: ParseError | IoError, line: int32) -> ConfigError {
    return match error {
        parse: ParseError => ConfigError { kind: 1, detail: parse.position * 100 + line },
        io: IoError => ConfigError { kind: 2, detail: io.code * 100 + line }
    };
}

func Load(text: int32, line: int32) -> int32 ! ConfigError {
    let value = Read(text) catch { e => throw ToConfig(e, line) };
    return value + 1;
}
```

`value? else (e => mapped)` is not a mapping form: it is `error: '? else' is not supported`, with `help: write 'value catch { e => throw mapped }'`.

## From absence to an error

`?` on an [optional](/docs/lang/optionals/propagation) passes on absence, never an error. When absence should be an error, the [coalescing](/docs/lang/optionals/coalescing) fallback says which one:

```rux
func PriceOf(code: int) -> int? {
    return if code == 1 { 250 } else { none };
}

func Total(code: int, count: int) -> int ! UnknownProduct {
    let price = PriceOf(code) ?? throw UnknownProduct { code };
    return price * count;
}
```

A function that returns `U? ! F` can pass on both: `!` passes an error on, and `?` on an optional returns `none`.

## `?` and `!`

The two postfix operators look alike and do different jobs:

| Operator | On          | Passes on | The enclosing function returns |
| -------- | ----------- | --------- | ------------------------------ |
| `x?`     | an optional | absence   | an optional, `-> U?`           |
| `x!`     | a fallible  | an error  | a fallible, `-> U ! F`         |

Each refuses the other's operand. `?` on a call that can fail is:

```text
error: '?' does not propagate errors
  help: write '!' to pass the error on
```

## Ownership

`x!` moves the success onward and the error to the caller with their move operations, so an error or success whose move is prohibited, or one that is a reference, is rejected at the `!` — when a generic is instantiated, too.
