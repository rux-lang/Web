# Errors

A function that can fail says so in its result type: `-> T ! E` returns a `T` or fails with an `E`. The error is an ordinary value of an ordinary type, and a call to the function evaluates to its _fallible_ `T ! E`, which holds one or the other. The caller deals with it where it calls — it [passes the error on](/docs/lang/errors/propagation) with `!`, [handles](/docs/lang/errors/handling) it there with `!!` or `catch`, or [keeps the outcome](/docs/lang/errors/fallible-values) as a value — and never by accident: an outcome nobody looks at is a compile error.

```text
fallible-type = type "!" type
result        = "->" type | "->" "!" type
throw-stmt    = "throw" expr ";"
```

| Signature                | Meaning                                                     |
| ------------------------ | ----------------------------------------------------------- |
| `func F() -> T ! E`      | returns a `T`, or fails with an `E`                         |
| `func F() -> !E`         | returns nothing, or fails with an `E`                       |
| `func F() -> T ! A \| B` | returns a `T`, or fails with an `A` or a `B` — an error sum |

Conditions that no caller could recover from — a broken invariant, a bug — are not errors in this sense. They stop the program with a [panic](/docs/lang/errors/panics).

## Declaring the error

`!` binds loosest of the type operators, after the postfix suffixes and `|`. Everything after it is the error, so a sum needs no parentheses there, and a `|` before it belongs to the success:

| Result type                         | Success              | Error                   |
| ----------------------------------- | -------------------- | ----------------------- |
| `-> int32 \| bool ! IoError`        | `int32 \| bool`      | `IoError`               |
| `-> int32 ! ParseError \| IoError`  | `int32`              | `IoError \| ParseError` |
| `-> int32? ! IoError`               | `int32?`             | `IoError`               |
| `-> int32 ! (IoError?)`             | `int32`              | an optional `IoError`   |
| `-> (int32 ! ParseError) ! IoError` | `int32 ! ParseError` | `IoError`               |

A suffix never reaches across `!`, and `!` does not chain. An optional error, or a fallible that is itself the success, is grouped:

```text
error: '?' cannot reach across '!'
  help: write 'T ! (E?)' for an optional error, or '(T ! E)?' for an optional result
error: '!' does not chain in a type
  help: group the inner fallible, as in '(T ! E) ! F'
```

The error is part of a function's signature — of functions and methods, of [constructors](/docs/lang/structs/constructors) (`-> Self ! E`), of [function types](/docs/lang/functions/function-types) such as `func(int32) -> int32 ! Closed`, and of [interface](/docs/lang/interfaces/overview) requirements, which an implementation matches exactly, error included. `T ! E` is also a type of its own: the value a call evaluates to, which can be stored, passed and returned like any other. See [Fallible values](/docs/lang/errors/fallible-values).

## Throwing

`throw value;` sends an error. It leaves the function through its error side, and the value converts to the error type the way a `return` value converts to the return type — so a member of an error sum is injected:

```rux
variant DivideError {
    ByZero,
    Inexact(int)
}

func ExactDivide(a: int, b: int) -> int ! DivideError {
    if b == 0 {
        throw .ByZero;
    }
    if a % b != 0 {
        throw .Inexact(a % b);
    }
    return a / b;
}

func Save(ok: bool) -> !IoError {
    if !ok {
        throw IoError { code: 28 };
    }
    PrintLine("saved");
}
```

| Write               | Produces                           |
| ------------------- | ---------------------------------- |
| `return value;`     | the success, `value`               |
| `throw error;`      | the error, and leaves the function |
| `return;`           | completion, in a function `-> !E`  |
| falling off the end | completion, in a function `-> !E`  |

A case written without its type, as in `throw .ByZero;`, takes the function's error type. When that is a sum, write the owner, as in `throw ParseError::Invalid(at)`. A unit error, in a function `-> T ! ()`, is thrown as `throw ();`.

`throw` leaves like `return`: the error is evaluated and captured first, then [deferred statements](/docs/lang/ownership/defer) run and live locals are [destroyed](/docs/lang/ownership/destructors). It needs a function that can fail:

```text
error: 'throw' needs a function that can fail, but 'Parse' returns 'int'
  help: declare '-> int ! E' on the function
```

`throw` is a statement, and also a whole arm body — of a `match` or `catch` arm — and the whole right side of [`??`](/docs/lang/optionals/coalescing) or `!!`, as in `lookup ?? throw NotFound {}`. In those places it produces no value and never decides the type of the result.

A function `-> !E` completes with the unit `()` when it returns or falls off its end; its result is the fallible `() ! E`. A function with no result type that cannot fail is a void function, and a type that merely contains the unit, such as `()?`, still needs a value. `fail value;` is `error: 'fail' is not supported`, with `help: write 'throw value;'`, and `fail` stays a reserved word.

## Error types

An error is an ordinary value of an ordinary type. There is no base error type, no error interface, and no implicit conversion between error types. Common choices:

| Error type                                  | Use it when                                                               |
| ------------------------------------------- | ------------------------------------------------------------------------- |
| a `struct`                                  | one kind of failure, with details: `IoError { code: 28 }`                 |
| a [`variant`](/docs/lang/variants/overview) | several named kinds, each with its own payload: `DivideError::Inexact(1)` |
| an [`enum`](/docs/lang/enums/overview)      | several kinds with no payload                                             |
| a [sum](/docs/lang/sums/overview), `A \| B` | the failures of several steps, each kept with its own type                |
| `()`                                        | only the fact of failure matters: `-> T ! ()`, `throw ();`                |

An error sum widens implicitly: an error passes on as itself, as a member of the sum, or as a smaller sum of its members. A public function usually names a [`variant`](/docs/lang/variants/overview) instead, so that its error does not change every time an internal step gains a failure, and so that it can carry the original cause; a [type alias](/docs/lang/types/aliases) of a sum hides none of its members.

## Calling a function that can fail

A call to a function that can fail evaluates to its fallible `T ! E`. Where it is used, one of four postfix forms takes it apart:

| Form               | What happens to the error                                                                                | Page                                         |
| ------------------ | -------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| `x!`               | passed on, out of the function; the expression continues with the success                                | [Propagation](/docs/lang/errors/propagation) |
| `x !! v`           | replaced by `v`, or by leaving with `return`, `throw` or `Panic`; `x !! none` makes the success optional | [Handling](/docs/lang/errors/handling)       |
| `x !!;`            | dropped, and the success with it                                                                         | [Handling](/docs/lang/errors/handling)       |
| `x catch { arms }` | handed to arms that match it, as a `match` would                                                         | [Handling](/docs/lang/errors/handling)       |

Or it is kept whole, `let kept = F();`, and taken apart later; see [Fallible values](/docs/lang/errors/fallible-values).

```rux
func Show(a: int, b: int) {
    let quotient = ExactDivide(a, b) catch {
        .ByZero => {
            PrintLine("division by zero");
            return;
        },
        .Inexact(rest) => {
            PrintLine("remainder {}", rest);
            return;
        }
    };
    PrintLine("= {}", quotient);
}

func Half(a: int) -> int ! DivideError {
    return ExactDivide(a, 2)! / 2;
}
```

A fallible is not its success, so `ExactDivide(12, 2) / 2` is a type error, and a call left on its own as a statement, `ExactDivide(12, 2);`, is one too — an error can never be ignored by accident:

```text
error: operator '/' cannot combine left operand 'int ! DivideError' with right operand 'int'
  help: pass the error on with '!', replace it with '!!', or handle it with 'catch { ... }'
error: 'ExactDivide' can fail with 'DivideError', and the result is not used
  help: pass the error on with '!', ignore it with '!!;', or handle it with 'catch { ... }'
```

The same holds for a method, constructor, operator or interface requirement that can fail, and for a call through a function value whose type declares an error.

## Errors are values

Rux errors do not unwind. A function that can fail returns its success or its error as one tagged value, so handling a call is a test of the tag and a branch: to the code that continues on success, and on failure to the arms written at the call, or out of the function as an ordinary return.

- Nothing walks the stack, and an error costs what a return costs: a tag test and a branch at each frame it passes.
- The error travels in the caller's result slot, never on the heap.
- A function that cannot fail returns its plain type, and a call to it has no tag test. Code that cannot fail pays nothing for errors elsewhere.
- An error leaves a function only where the source says so — a `throw`, an `x!`, or an arm or fallback that throws — so every early exit is visible.

A fallible is stored as an 8-byte tag followed by the success or the error, aligned for the larger; `sizeof(int ! IoError)` is 16. The tag values are not a stable ABI. See [Layout](/docs/lang/memory/layout).

## Main cannot fail

[`Main`](/docs/lang/functions/main) has exactly one signature, `func Main() -> int`: its result is the process's exit status, and it cannot fail. The steps that can fail go in a function of their own, and `Main` chooses the exit status for its error:

```rux
func Run() -> !IoError {
    Save(true)!;
    Save(false)!;
}

func Main() -> int {
    Run() !! return 1;
    return 0;
}
```

When the helper returns the status itself, `Run() -> int ! IoError`, the whole of `Main` is `return Run() !! 1;`. A `Main` that can fail is refused, with that shape as its help:

```text
error: 'Main' must be 'func Main() -> int', but it returns 'int ! IoError'
  note: the result of 'Main' is the process's exit status
  help: move the steps that can fail into a function and handle its error in 'Main', as in 'return Run() !! 1;'
```

Nothing is printed for an error that `Main` replaces with a status. To tell the user what went wrong, handle it with `catch` and report it there before returning.
